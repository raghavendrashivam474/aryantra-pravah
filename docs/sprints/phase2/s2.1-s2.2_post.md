## 1. Executive Summary

S2.1 and S2.2 establish the first two layers of the Pravah protocol stack: a logical message representation and a deterministic binary wire format. Before these sprints, the transport layer moved raw `byte[]` with no structure. After these sprints, there is a clean `Message ↔ byte[]` mapping that is fully tested, documented, and transport-independent.

No existing Phase 0 or Phase 1 code was modified. No framing, chat semantics, encryption, or transport changes were introduced. The sprint boundaries were respected strictly.

## 3. Architecture Decisions

### 3.1 Package Placement

Protocol code lives in `com.aryntra.pravah.protocol`, sibling to `transport` and `core`. This enforces the layering:

```
Application (future)
    ↓
Protocol (com.aryntra.pravah.protocol)   ← NEW
    ↓
Transport (com.aryntra.pravah.transport)
    ↓
TCP (com.aryntra.pravah.transport.tcp)
```

No protocol class imports anything from `transport`. No transport class was modified to know about `Message`.

### 3.2 Message as Java Record

`Message` is a `record` (Java 21), which gives us:
- Immutability by default
- Structural equality (overridden for `byte[]` payload via `Arrays.equals`)
- Compact canonical constructor for validation
- No boilerplate

The `payload()` accessor is overridden to return a defensive clone, preventing external mutation of internal state. The compact constructor also clones on ingestion.

### 3.3 Identity Separation

Three distinct identity concepts are kept separate:

```
TCP connection ID (socket address, transport-internal)
    ≠
senderId (logical peer identity, protocol-level)
    ≠
messageId (unique per logical message)
```

The `senderId` is a protocol-level string, not a socket address. This is deliberate: when Bluetooth or LAN transports are added later, the same `senderId` can traverse different transports without changing.

### 3.4 Single Exception Type

`ProtocolException` extends `PravahException`. One type covers all wire-format violations (bad magic, bad version, unknown type, truncation, trailing bytes, negative lengths). This avoids an explosion of exception subclasses for what is fundamentally one failure mode: "this byte sequence is not a valid Pravah message."

### 3.5 No Framing

This is the most important architectural non-decision. S2.2 operates on complete `byte[]` in isolation. It does not read from streams, does not buffer, does not detect message boundaries in a TCP byte stream. That problem belongs to S2.3 and requires different solutions (length-prefix framing, delimiter framing, etc.). Prematurely coupling encoding to framing would create the exact kind of leaky abstraction the sprint boundaries exist to prevent.

## 4. Wire Format Summary (v1)

```
[MAGIC: 2B "PR"] [VERSION: 1B 0x01] [TYPE: 1B]
[SENDER_LEN: 2B unsigned] [SENDER: N bytes UTF-8]
[MSGID_LEN: 2B unsigned]  [MSGID: M bytes UTF-8]
[PAYLOAD_LEN: 4B signed]  [PAYLOAD: P bytes]
```

- **Endianness:** Big-Endian (network byte order) for all multi-byte integers
- **String encoding:** UTF-8, no BOM, no null terminator
- **Minimum size:** 12 bytes (theoretical; practical minimum is larger due to non-blank validation)
- **Determinism guarantee:** Same `Message` → same `byte[]` every time, verified by test

Full specification with hex dump example is in `docs/protocol/wire-format-v1.md`.

## 5. Test Coverage Detail

**Total: 42 tests (20 existing + 22 new), 0 failures, 0 errors**

### S2.1 Tests (8 new)

- **MessageType:** All 3 codes resolve correctly; unknown code `0x99` throws `IllegalArgumentException` with hex-formatted message.
- **Message construction:** Valid messages construct successfully with all fields preserved.
- **Null rejection:** All 4 fields independently tested — each null throws `NullPointerException`.
- **Blank rejection:** Empty string and whitespace-only string both rejected for `senderId` and `messageId`.
- **Defensive copying:** Mutating the input array after construction does not affect the message. Mutating the array returned by `payload()` does not affect the message.
- **Equality:** Two messages with identical fields (but different `byte[]` instances) are equal and have the same hash code. Messages differing in payload or sender are not equal. Null and wrong-type comparisons return false.

### S2.2 Tests (14 new)

- **Encoder null check:** `encode(null)` throws `NullPointerException`.
- **Encoder header verification:** First 4 bytes of any encoded message are `0x50 0x52 0x01 <type_code>`.
- **Encoder determinism:** Encoding the same message 3 times produces 3 identical byte arrays.
- **Parser null check:** `parse(null)` throws `NullPointerException`.
- **Parser truncation:** 5-byte input rejected as smaller than 12-byte minimum.
- **Parser bad magic:** `0x58 0x59` ("XY") rejected with specific error message showing expected vs actual bytes.
- **Parser bad version:** Version `0x09` rejected with expected vs actual version in error message.
- **Parser unknown type:** Type code `0x7F` rejected; error chains to `MessageType.fromCode()` failure.
- **Parser trailing bytes:** Valid encoded message + 1 garbage byte appended → rejected with "Trailing bytes detected."
- **Round-trip JOIN:** Empty payload, round-trips cleanly.
- **Round-trip MESSAGE:** 74-byte ASCII payload, round-trips cleanly.
- **Round-trip LEAVE:** 23-byte ASCII payload, round-trips cleanly.
- **Round-trip Unicode:** Emoji and multi-byte UTF-8 in both identifiers and payload, round-trips cleanly.
- **Round-trip payload sizes:** 0, 1, 127, 256, 1024, and 65535 byte payloads all round-trip correctly.

## 7. Known Limitations & Future Considerations

1. **String length ceiling:** `senderId` and `messageId` are limited to 65,535 UTF-8 bytes by the 2-byte unsigned length prefix. This is more than sufficient for any realistic identifier but is a hard protocol limit.

2. **Payload length ceiling:** 2,147,483,647 bytes (Java `int` max). The 4-byte signed prefix could theoretically be extended to 8 bytes in a future version if needed.

3. **No forward compatibility for unknown types:** The parser currently rejects unknown type codes. A future version may want to support "skip unknown types" for forward compatibility. This is a deliberate strictness choice for v1 — predictable failure over silent misinterpretation.

4. **No compression:** Payloads are stored verbatim. Large payloads will produce proportionally large wire representations. Compression can be added as a payload-level concern without changing the wire format structure.

5. **No authentication or integrity:** The wire format carries no MAC, signature, or checksum. Any byte corruption will either cause a parse failure (if structural) or silently corrupt payload data. Integrity protection is a future security layer concern.

## 9. Suggested Next Steps (S2.3 Preview)

S2.3 — Message Framing will need to solve:

```
TCP byte stream (continuous, no boundaries)
        ↓
    Frame Extractor
        ↓
Complete byte[] per message
        ↓
    MessageParser (S2.2, already exists)
        ↓
    Message
```

Key decisions for S2.3 will include:
- Framing strategy (length-prefix envelope vs delimiter vs hybrid)
- Where the frame buffer lives (per-connection, inside or outside transport)
- How to integrate with `TransportListener.onDataReceived()` which currently delivers arbitrary TCP read chunks
- Whether `TransportListener` needs a new method or an adapter layer

None of this was started in S2.1/S2.2. The encoder and parser are ready to be consumed by whatever framing solution S2.3 chooses.
