# Sprint S4.1–S4.3 — Application Messaging Layer

## Objective

Build the **application communication layer** on top of the frozen Phase 3 peer substrate. Phase 3 (v0.3.6, 179/179 tests) established *how peers find, connect to, and exchange protocol envelopes with each other*. Phase 4's mandate was to answer the next three questions without touching a single Phase 3 file:

| Sprint | Question |
|--------|----------|
| **S4.1** | What is an application message, and how does an application send/receive one without knowing about TCP, sockets, or frames? |
| **S4.2** | What is a conversation, and which peers belong to it? |
| **S4.3** | What happened to this message, and how do we know? |

The strict constraint: Phase 3 is a **protected foundation**. No transport, peer identity, discovery, presence, routing, framing, or protocol contracts may be redesigned merely to make application-layer implementation easier.

- **Release:** v0.3.6 (Phase 3 complete, frozen)
- **Tests:** 179/179 passing
- **Architecture at baseline:**

```text
Application (empty — no application layer existed)
    ↓

    ↓

    ↓

    ↓

    ↓

```

- **Key protocol contracts:**
  - `Message(MessageType type, String senderId, String messageId, byte[] payload)` — the only wire-level message record
  - `MessageType` enum: `JOIN`, `MESSAGE`, `LEAVE`
  - `ProtocolListener` callbacks: `onPeerJoined`, `onMessageReceived`, `onPeerLeft`
  - `PeerRouter.send(PeerId destination, Message message)` — the only outbound routing API
  - `PeerConnectionCoordinator.setProtocolListener(ProtocolListener)` — the only inbound hook

- **Critical architectural invariant:** `PeerId ≠ connectionId`. The peer system addresses logical identities; the transport addresses sockets. The application layer must respect this separation.

## Implemented Capability

### S4.1 — Application Messaging Boundary

**Problem:** The protocol layer knows how to transport a `Message` envelope, but the application has no representation of a user-facing message. Without a boundary, application code would need to import `TcpTransport`, `FrameEncoder`, and `MessageEncoder` directly — violating the dependency direction principle.

**Solution:** Introduced package `com.aryntra.pravah.messaging` with four classes:

1. **`ApplicationMessage`** — Immutable domain model carrying `messageId`, `sender` (`PeerId`), `content` (String), `timestamp` (`Instant`), and `conversationId`. Factory methods `text()` and `fromPayload()` handle construction. Payload serialization uses UTF-8 encoding. Equality is based on `messageId`, `sender`, `content`, and `conversationId` (timestamp excluded for value semantics).

2. **`ApplicationMessageListener`** — `@FunctionalInterface` callback with a single method `onMessage(ApplicationMessage)`.

3. **`ApplicationMessagingService`** — Interface defining `send(PeerId, ApplicationMessage)`, `sendText(PeerId, String)`, `addListener()`, and `removeListener()`.

4. **`DefaultApplicationMessagingService`** — Production implementation that:
   - **Outbound:** Converts `ApplicationMessage` → protocol `Message` (type `MESSAGE`, payload = UTF-8 content bytes) → `PeerRouter.send()`. The caller never touches `TcpTransport`, `Socket`, `connectionId`, or `FrameEncoder`.
   - **Inbound:** Registers a `ProtocolListener` on the `PeerConnectionCoordinator`. When `onMessageReceived` fires, it reconstructs an `ApplicationMessage` from the protocol payload and dispatches to registered `ApplicationMessageListener`s.

**Key design rule enforced:** The application layer routes exclusively through `PeerRouter`. Direct access to `TcpTransport` or `PeerConnectionCoordinator` from application code is architecturally prohibited.

**Tests added:** 9 (5 validation/construction, 1 equality, 3 service unit tests including stub-transport routing verification and inbound dispatch through `coordinator.onDataReceived()`).

### S4.2 — Conversation Model

**Problem:** Application messages need a stable logical container. A raw `PeerId` pair is insufficient — the application needs a first-class `Conversation` entity to organize message history, UI state, and future features (read receipts, typing indicators, group membership).

**Critical distinction:** `Peer ≠ Conversation`. A peer is an identity. A conversation is a relationship context involving one or more peers.

**Solution:** Three new classes in `com.aryntra.pravah.messaging`:

1. **`ConversationId`** — Java `record` wrapping a non-blank `String` value. Serves as the stable, unique identifier for a conversation.

2. **`Conversation`** — Immutable container holding a `ConversationId` and an unmodifiable `Set<PeerId>` of participants. Constructor enforces invariants:
   - Exactly 2 participants (direct conversation; group chat is explicitly out of scope for Phase 4)
   - Participants must be distinct (no duplicates)
   - No null values

3. **`ConversationManager`** — Thread-safe (`ConcurrentHashMap`) manager providing:
   - `getOrCreateDirectConversation(PeerId target)` — retrieves or creates a conversation
   - `getConversation(ConversationId)` — lookup by ID
   - `listConversations()` — all active conversations
   - `removeConversation(ConversationId)` — lifecycle cleanup
   - `deriveDirectConversationId(PeerId, PeerId)` — **static, deterministic, order-independent** canonical ID derivation. Lexicographically sorts peer values to guarantee `alice ↔ bob` and `bob ↔ alice` resolve to the identical `ConversationId("direct:alice:bob")`.

**Architectural decision documented:** Self-conversations (`Peer A ↔ Peer A`) are explicitly rejected with `IllegalArgumentException`. The brief instructed: "Do not silently invent semantics."

**`ApplicationMessage` integration:** The `ApplicationMessage` constructor was extended to accept a `ConversationId` parameter. Backwards-compatible 4-argument overloads delegate to a default system conversation ID, preserving all existing S4.1 call sites.

**Tests added:** 8 (3 conversation invariant tests, 5 manager tests including canonical ID reconciliation, self-conversation rejection, lookup, and removal).

### S4.3 — Message Lifecycle & Delivery Receipts

**Problem:** These states are **not** equivalent:

```text
Application created message
    ≠
PeerRouter accepted message
    ≠
Remote peer received bytes
    ≠
Remote application parsed message
    ≠
Human saw message
```

Collapsing all of them into a single `DELIVERED` flag would be architecturally dishonest. The sprint brief demanded explicit lifecycle semantics with evidence-based state transitions.

**Solution:** Two new types and a significant extension to `DefaultApplicationMessagingService`:

1. **`MessageState`** — Enum: `CREATED`, `SENT`, `DELIVERED`, `FAILED`.

2. **`MessageLifecycleListener`** — `@FunctionalInterface` with `onStateChanged(String messageId, MessageState newState)`.

3. **`DefaultApplicationMessagingService` lifecycle engine:**
   - **State tracking:** In-memory `ConcurrentHashMap<String, MessageState>` maps outgoing `messageId`s to their current lifecycle state.
   - **Outbound flow:** `send()` transitions the message to `CREATED`, constructs the protocol envelope, calls `PeerRouter.send()`, and transitions to `SENT`. If routing throws (e.g., peer not in registry), the state transitions to `FAILED`.
   - **Application-level ACK framing (ADR-005):** To avoid modifying the frozen Phase 3 protocol, application payloads use a 1-byte type prefix inside the existing `MESSAGE` envelope:
     - `0x01` (`APP_MSG_CHAT`): Followed by UTF-8 text content
     - `0x02` (`APP_MSG_ACK`): Followed by UTF-8 `messageId` of the acknowledged message
   - **Inbound chat handling:** When a `0x01` payload arrives, the service strips the type byte, reconstructs the `ApplicationMessage` (with canonical `ConversationId` derived from local + remote `PeerId`), dispatches to `ApplicationMessageListener`s, and **automatically sends a `0x02` ACK** back to the sender via `PeerRouter`.
   - **Inbound ACK handling:** When a `0x02` payload arrives, the service extracts the acknowledged `messageId`, transitions the tracked state to `DELIVERED`, and fires `MessageLifecycleListener` callbacks.

**What was explicitly NOT built (per brief):**
- Retry engine, backoff, offline queue, store-and-forward
- Read receipts, typing indicators
- Exactly-once delivery guarantees
- Protocol-level `MessageType.ACK` (would have violated the frozen-foundation constraint)

**Tests added:** 2 unit tests (FAILED state on unroutable peer, DELIVERED state on inbound ACK) + 1 full end-to-end integration test over real TCP.

## Integration Test: Full Bidirectional Lifecycle

The integration test (`ApplicationMessagingIntegrationTest`) exercises the complete S4.1→S4.3 flow over real TCP:

1. Two `TcpTransport` instances start on ephemeral ports
2. Full peer infrastructure is wired for both Alice and Bob (registry, presence, coordinator, router, messaging service)
3. Mutual `JOIN` handshake establishes bidirectional protocol sessions (matching Phase 3's `EndToEndPeerIntegrationTest` pattern)
4. Alice calls `aliceMessaging.sendText(bobId, "Pravah Application Layer Verified!")`
5. Assertion: message state transitions to `SENT`
6. Bob's `ApplicationMessageListener` fires with the correct `messageId`, `sender`, `content`, and canonical `ConversationId`
7. Bob's service automatically dispatches an ACK back to Alice
8. Alice's `MessageLifecycleListener` fires with `DELIVERED`
9. Assertion: `aliceMessaging.getMessageState(sentMsg.messageId()) == MessageState.DELIVERED`

**The application layer never imports `TcpTransport`, `Socket`, `FrameEncoder`, or `connectionId`.**

## Key Architectural Decisions

1. **Application boundary via `PeerRouter`, not `TcpTransport`:** The application layer addresses peers by `PeerId`, never by socket. This preserves the Phase 3 abstraction.

2. **Canonical conversation identity:** `ConversationManager.deriveDirectConversationId()` lexicographically sorts peer values, guaranteeing order-independent identity. `alice ↔ bob` and `bob ↔ alice` produce the same `ConversationId`.

3. **Application ACK framing over protocol modification (ADR-005):** Rather than adding `MessageType.ACK` to the frozen wire format, we prefix application payloads with a type byte (`0x01` CHAT / `0x02` ACK) inside the existing `MESSAGE` envelope. This keeps Phase 3 untouched while enabling delivery receipts.

4. **No persistence, no retries, no offline queue:** Phase 4 is deliberately narrow. The lifecycle is in-memory only. Persistence belongs to Phase 5.
