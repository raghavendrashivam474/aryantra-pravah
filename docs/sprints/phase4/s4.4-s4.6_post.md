## 2. Sprint Deliverables

### 2.1 S4.4 — Message History & Persistence

**Objective:** Move application messages from ephemeral in-memory objects to a durable conversation history that survives process restart.

#### Design Decision: Abstraction Before Implementation

Before touching any storage code, an abstraction layer was introduced. This was documented in **ADR-006 (Message History Persistence Boundary)**. The reasoning was as follows:

- Embedding SQLite calls directly into `DefaultApplicationMessagingService` would have violated the intended dependency direction (Application → Messaging → Protocol → Peer → Transport). Instead, it would have created a hidden dependency (Application Messaging → JDBC), making the messaging service untestable without a live database and creating a portability obstacle for the future Android target where the SQLite API surface differs.
- A file-based serialization approach (`ObjectOutputStream` or JSON) was rejected because it offers no queryability, no deterministic ordering guarantee, and fragile schema evolution.
- A full ORM (JPA/Hibernate) was rejected because it introduces a massive transitive dependency tree, contradicts the Phase 0 zero-dependency posture, and is architectural overkill for a single-table use case.

The selected design is an interface, `MessageHistoryStore`, with two implementations. The application messaging layer depends only on the interface.

#### Files Added

**Source (`src/main/java/com/aryntra/pravah/messaging/`):**

- `MessageHistoryStore.java` — The persistence contract. Six operations: `save`, `find`, `getConversationHistory`, `updateState`, `findState`, `delete`. No storage-technology leakage in the interface.
- `InMemoryMessageHistoryStore.java` — Thread-safe reference implementation backed by `ConcurrentHashMap`. Uses an `AtomicLong` sequence counter to guarantee deterministic ordering even when multiple messages share identical `Instant` timestamps (a real risk on fast local exchanges).
- `SqliteMessageHistoryStore.java` — Durable implementation using `org.xerial:sqlite-jdbc:3.45.2.0`. Implements `AutoCloseable` for deterministic resource cleanup. Schema is minimal and application-focused:

```sql
CREATE TABLE IF NOT EXISTS messages (
    seq INTEGER PRIMARY KEY AUTOINCREMENT,
    message_id TEXT NOT NULL UNIQUE,
    conversation_id TEXT NOT NULL,
    sender_id TEXT NOT NULL,
    content TEXT NOT NULL,
    timestamp_epoch_ms INTEGER NOT NULL,
    state TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_messages_conv_seq
ON messages(conversation_id, seq);
```

Note that the schema deliberately contains **no** `connection_id`, `socket`, `port`, or any transport-layer artifact. `sender_id` stores `PeerId.value()` — logical identity only. This upholds the Phase 3 rule that `PeerId ≠ connectionId`.

**Source (`src/main/java/com/aryntra/pravah/messaging/`) modified:**

- `DefaultApplicationMessagingService.java` — A new constructor was added that accepts a `MessageHistoryStore`. The zero-argument constructor path continues to work by defaulting to `InMemoryMessageHistoryStore`, preserving the existing S4.1–S4.3 tests unchanged. Outbound sends now persist as `CREATED` before routing and transition to `SENT` upon successful dispatch (or `FAILED` on routing exception). Inbound messages are persisted as `DELIVERED` before listener notification and ACK dispatch.

**Tests added:**

- `MessageHistoryStoreTest.java` — 14 contract tests: save/find, duplicate rejection, null handling, conversation-scoped history retrieval, ordering, state transitions, missing-message behavior, and delete semantics.
- `SqliteMessageHistoryStoreTest.java` — 6 tests using JUnit 5 `@TempDir`: basic operations, ordering under identical timestamps, and the critical restart-durability test that closes the store, opens a fresh instance against the same file, and verifies full recovery.
- `ApplicationMessagePersistenceIntegrationTest.java` — 1 end-to-end integration test exercising the full stack (TCP transport, peer coordinator, peer router, SQLite store) to prove that a real network message round-trip persists correctly on both sender and receiver and survives store recreation.

**Dependency added:** `org.xerial:sqlite-jdbc:3.45.2.0` in `pom.xml`. This is the first runtime dependency in the project's history. It was introduced deliberately, is isolated to `SqliteMessageHistoryStore`, and does not leak into any other class. All other code paths (including all tests except the SQLite-specific ones) work without invoking the JDBC driver.

### 2.2 S4.5 — Group Communication

**Objective:** Generalize application-level messaging from strictly 2-party direct conversations to N-party groups, without breaking existing direct conversation semantics.

#### Design Decision: Additive, Not Generalizing

The brief presented three options: (A) generalize `Conversation` to support 2+ participants; (B) keep direct conversations as-is and introduce a separate `GroupConversation`; (C) introduce a discriminator (`DIRECT | GROUP`) on `Conversation`.

**Option (B) was selected** and documented in **ADR-007 (Group Conversation Model & Application Framing)**. Rationale:

- The existing `Conversation` class enforces an invariant: `participants.size() == 2` and participants must be distinct. This invariant is enforced by test suite `ConversationTest` (3 tests) which explicitly asserts that a 3-participant construction throws. Loosening this invariant would have required modifying an existing test's assertion — precisely the "fix by weakening" antipattern the sprint brief prohibits.
- Direct conversations have a canonical identity derivation (`direct:alice:bob`, lexically sorted) that groups fundamentally do not share. Groups have opaque, UUID-based identity (`group:<uuid>`) because they are not defined by their participant set — a group with participants `{A,B,C}` that removes `A` is still the same group, not a new one.
- Keeping the two models separate preserves clarity: `Conversation` remains a value-like object with a fixed shape; `GroupConversation` is an entity with a mutable participant set.

#### Files Added

**Source:**

- `GroupConversation.java` — Domain model. Holds a stable `ConversationId` (format: `group:<UUID>`), a human-readable name, and a `CopyOnWriteArraySet<PeerId>` of participants. Provides `addParticipant`, `removeParticipant`, `hasParticipant`, `participantCount`, and returns unmodifiable snapshots of the participant set. Enforces that the last participant cannot be removed (would create a ghost group). Equality is defined strictly by `conversationId`, not by name or membership — a group's identity survives all membership changes, matching the ADR-007 contract.

**Source modified:**

- `ConversationManager.java` — Extended with `createGroup(name, initialParticipants)`, `registerGroupConversation(group)`, `getGroupConversation(id)`, and `listGroupConversations()`. The `createGroup` method automatically injects the local peer into the participant set (a group creator is by definition a member). The direct-conversation API (`getOrCreateDirectConversation`, `deriveDirectConversationId`, `getConversation`, `listConversations`, `removeConversation`) is unchanged; all 5 pre-existing `ConversationManagerTest` tests continue to pass unmodified.
- `DefaultApplicationMessagingService.java` — Extended with group send path and wire framing. The application-level protocol now supports three payload types, distinguished by a leading byte:

  | Byte | Type | Payload layout |
  |---|---|---|
  | `0x01` | `APP_MSG_CHAT` (direct) | `[0x01][content UTF-8]` |
  | `0x02` | `APP_MSG_ACK` (delivery receipt) | `[0x02][acked message-id UTF-8]` |
  | `0x03` | `APP_MSG_GROUP_CHAT` | `[0x03][groupId length: 2 bytes big-endian][groupId UTF-8][content UTF-8]` |

  The group send path performs application-level fan-out: it looks up participants from the local `ConversationManager`, excludes the local peer, and issues one `peerRouter.send()` per remote participant. This deliberately avoids modifying `PeerRouter` — the fan-out is an application concern, not a routing concern. Inbound `0x03` messages decode the embedded `groupId`, reconstruct an `ApplicationMessage` tagged with the group's `ConversationId` (not a derived direct ID), persist it, notify listeners, and reply with a per-recipient `0x02` ACK to the sender. Auto-reconciliation ensures a group is registered locally on first inbound receipt.

**Tests added:**

- `GroupConversationTest.java` — 7 tests across three nested classes: creation & validation (nulls, blanks, empty participant sets, factory helper uniqueness), participant lifecycle (add/remove, duplicate detection, last-participant guard, unmodifiable snapshots), and equality-by-identity.
- `ConversationManagerTest.java` — Extended with 3 additional tests: group creation with automatic sender inclusion, dynamic group registration, and group listing/removal. All 5 pre-existing tests continue to pass.
- `ApplicationGroupMessagingIntegrationTest.java` — 1 end-to-end integration test exercising a 3-peer TCP mesh (Alice ↔ Bob, Bob ↔ Charlie, Alice ↔ Charlie), group creation, fan-out from Alice, independent reception at Bob and Charlie, and durable persistence at all three nodes after store closure and reopen.

**Documentation added:**

- `docs/adr/ADR-007-group-conversation-model.md`

#### Delivery Semantics Decision

As explicitly required by the brief, the meaning of `DELIVERED` for group messages was defined and documented rather than silently chosen. The selected semantics: **`DELIVERED` transitions when at least one recipient's ACK arrives.** Rationale:

- Requiring all-recipient ACKs would block state progression on the slowest or offline participant, which is unrealistic for a peer-to-peer chat system without a delivery aggregator.
- Requiring per-recipient state would multiply the state model complexity and demand a change to `MessageState` enum (currently `CREATED | SENT | DELIVERED | FAILED`) — an ADR-worthy change deferred to a future phase.
- The chosen "at-least-one" semantic is honest: it accurately reports that the message has been observed by at least one intended party. Future phases may layer per-recipient tracking on top without breaking this contract.

### 2.3 S4.6 — Complete Application End-to-End Integration

**Objective:** Prove the application layer as a coherent whole through a single grand acceptance test exercising the real stack.

#### Files Added

**Test:**

- `Phase4EndToEndApplicationIntegrationTest.java` — The Phase 4 acceptance test. It builds a 3-peer mesh using a private `ChatPeerNode` helper class that wires every layer of the stack: `TcpTransport`, `PeerRegistry`, `PeerPresenceManager`, `PeerPresenceBridge`, `PeerConnectionCoordinator`, `PeerRouter`, `SqliteMessageHistoryStore` (file-backed via `@TempDir`), and `DefaultApplicationMessagingService`. The test executes four stages:

  **Stage 1 — Direct Messaging & Lifecycle.** Alice sends `"Stage 1: Direct Hello Bob!"` to Bob within the canonical direct conversation `direct:alice:bob`. The test asserts that Alice's message state transitions `SENT` → `DELIVERED` upon Bob's ACK arrival, Bob's listener receives the message with correct `messageId`, `sender`, `content`, and `conversationId`.

  **Stage 2 — Group Fan-Out.** Alice creates a group `"Core Team"` with Bob and Charlie. Bob and Charlie register the same group locally (simulating group membership sync). Alice dispatches a group message. The test asserts that both Bob and Charlie receive the message exactly once, tagged with the group `ConversationId` (not a direct one), and that all three nodes persist the message under the group context in their respective SQLite stores.

  **Stage 3 — Disconnect & Reconnect Resilience.** Alice's TCP transport is stopped, simulating a network drop. A fresh `ChatPeerNode` for Alice is instantiated on a new port, and the connect+JOIN handshake is re-executed against Bob. Alice sends a second direct message `"Stage 3: Post-reconnect message!"`. The test asserts Bob receives it under the same `direct:alice:bob` conversation ID — proving that conversation identity is a logical construct that survives transport-layer replacement, exactly as the Phase 3 principle `PeerId ≠ connectionId` requires.

  **Stage 4 — Grand Durability Check.** All active peer nodes are cleanly closed. Fresh `SqliteMessageHistoryStore` instances are opened against the exact same database files. The test asserts:
  - Alice's `direct:alice:bob` history contains both messages (Stage 1 pre-reconnect + Stage 3 post-reconnect) in deterministic insertion order.
  - Bob's `direct:alice:bob` history matches Alice's exactly.
  - Alice's, Bob's, and Charlie's group histories all contain the Stage 2 group message correctly.
  - All persisted message states are `DELIVERED`.

  This single test covers every DoD item for S4.6.

- `docs/reports/PHASE_4_REPORT.md` — Formal completion report (this document's source material, in Markdown form for repository archival).

## 3. Notable Issues Encountered & Resolution

### 3.1 PowerShell UTF-8 BOM Corruption

During the initial S4.4 file creation, PowerShell 5.1's `Set-Content -Encoding UTF8` cmdlet silently prepended a UTF-8 Byte Order Mark (`\uFEFF`) to every Java source file. `javac` correctly rejected these files with `illegal character: '\ufeff'`. Resolution: switched all file writes to `[System.IO.File]::WriteAllText(path, content, new UTF8Encoding($false))`, which writes UTF-8 without a BOM. A verification step was added to check the first three bytes of each generated `.java` file before compilation.

### 3.2 Constructor Signature Mismatch in Test Fixtures

The initial `ApplicationMessagePersistenceIntegrationTest` was written using assumed constructor signatures for `PeerPresenceManager`, `PeerConnectionCoordinator`, and `PeerRouter`. Compilation failed because the assumed signatures did not match the frozen Phase 3 contracts. Rather than modifying the Phase 3 classes to accommodate the test (which would have violated the sprint's non-negotiable architectural rule), the test was rewritten by inspecting `ApplicationMessagingIntegrationTest.java` (the reference S4.1–S4.3 test) and matching its exact wiring pattern. This preserved Phase 3 as a protected foundation.

### 3.3 SQLite File Locking on Windows During E2E Test

The first draft of `Phase4EndToEndApplicationIntegrationTest` closed the SQLite stores mid-test (Stage 3), then attempted further messaging in Stage 4 that indirectly triggered store reads. On Windows, SQLite holds file locks even after JDBC connection closure until the JVM garbage-collects the underlying native handle. This caused `SQLException: database connection closed` and a JUnit `@TempDir` cleanup failure. Resolution: the test was restructured so that all messaging stages (direct, group, and reconnect-resume) complete against **live** stores, and the closure and re-opening for durability verification happens as the final stage of the test. This ordering eliminates any window during which a closed connection could be re-used.

### 3.4 Assertion Refinement After Behavioral Discovery

After the SQLite locking issue was resolved, one assertion in the E2E test still failed: it expected Alice's direct history to contain 1 message post-recovery, but the actual value was 2. This was correct behavior, not a bug — Alice's Stage 3 reconnected node writes to the same `alice_chat.db` file as the original Alice, so both her pre-reconnect and post-reconnect messages are persisted. The assertion was corrected to expect 2 messages in deterministic order. This is precisely the kind of resolution the sprint brief mandates: identify why a test fails, determine which side represents correct behavior, and update the test only when the code's behavior is architecturally right.

## 5. Dependency Policy Change

Phase 4 introduces exactly one runtime dependency: `org.xerial:sqlite-jdbc:3.45.2.0`. Before this sprint, the project had zero runtime dependencies (JUnit 5 is `test`-scope only). The addition is:

- **Isolated** — used exclusively by `SqliteMessageHistoryStore.java`.
- **Swappable** — the `MessageHistoryStore` abstraction means alternative implementations (Android SQLite, remote KV store, encrypted store) can replace it without touching the messaging service.
- **Justified** — Android portability is a stated project goal; SQLite is the natural fit both on Windows/Linux (via `sqlite-jdbc`) and on Android (via the platform's `android.database.sqlite` API), so this choice aligns rather than conflicts with the mobile roadmap.
- **Documented** — recorded in ADR-006 with alternatives explicitly considered and rejected.

## 6. Out of Scope (Deferred to Later Phases)

The following capabilities were deliberately not implemented, in accordance with the sprint brief:

- Offline message queueing, retry engines, store-and-forward buffering
- Message-history sync protocol between disconnected peers
- Conflict resolution for concurrent group membership edits
- Encryption at rest for the SQLite database
- Full-text or metadata search over conversation history
- Attachment storage (blobs, media)
- Group administrative roles, moderation, invitation flows, read receipts, typing indicators
- Per-recipient delivery state tracking for group messages
- Any UI or CLI frontend

Each of these deserves its own architectural review before implementation.

## 9. Handoff Notes

The Phase 4 codebase is ready for consumption by any future frontend (Android, desktop, CLI, or web). Consumers should interact exclusively with:

- `ApplicationMessagingService` (public interface) — for sending messages and subscribing to inbound events
- `DefaultApplicationMessagingService` (concrete impl) — instantiated with a `PeerId`, `PeerRouter`, `PeerConnectionCoordinator`, and optionally a `MessageHistoryStore` (defaults to in-memory)
- `ConversationManager` (accessible via `messagingService.getConversationManager()`) — for creating direct conversations, groups, and querying membership
- `MessageHistoryStore` (accessible via `messagingService.getHistoryStore()`) — for querying persisted conversation history
- `ApplicationMessage`, `ConversationId`, `MessageState`, `GroupConversation` — domain models

Consumers should **not** import from `com.aryntra.pravah.transport.*`, `com.aryntra.pravah.protocol.*`, or the lower-level peer classes. The messaging layer is the intended API surface.

The next natural phase can proceed in one of several directions — mobile frontend, offline queueing and reconciliation, encryption, or federation — each independently addressable without disturbing the Phase 3 or Phase 4 substrate.
