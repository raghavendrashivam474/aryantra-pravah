The Phase 5 extension has been completed successfully. The Pravah system has evolved from *"Applications can reliably deliver messages even when the destination peer is temporarily unavailable, across process restarts and network reconnections"* (end of S5.3, `v0.5.0`) into *"Applications can reliably deliver messages with bounded retry policies, observe delivery attempts in real-time without disrupting them, and deliver reliably to multi-recipient groups with per-recipient state and independent retry"* (end of S5.6, `v0.5.6`).

The reliability layer's existing contracts (`OutboxState`, `OutboxEntry`, `DeliveryOutbox`) were extended additively and remain backward-compatible with the S5.1–S5.3 baseline.

Two new Architectural Decision Records were produced during this sprint extension:

- **ADR-009 — Bounded Delivery Retry and Abandonment:** Formalizes the introduction of the `ABANDONED` outbox state, per-entry attempt counting, and the configurable `maxAttempts` policy that terminates automatic retry sweeps.

## 2. Sprint Deliverables

### 2.1 S5.4 — Bounded Retry & Dead-Letter

**Objective:** Introduce a bounded automatic retry policy so that permanently unavailable peers do not cause pending delivery intents to accumulate indefinitely and be retried on every future reconnection event forever.

#### Design Decision: Extend `OutboxState` with `ABANDONED`

Before writing any implementation code, the architectural question was analyzed: *should the terminal "give up" state be represented as a new `OutboxState` value, or should it live on `MessageState`, or should it be a boolean flag on `OutboxEntry`?*

The S5.3 `OutboxState` enum contained only `PENDING` and `COMPLETED`. Two dimensions of information are needed after the change:

1. **Is this delivery work still eligible for automatic retry?** (PENDING vs. not-PENDING)
2. **Why did it stop being eligible?** (COMPLETED via ACK, or ABANDONED via exhausted retries)

A boolean `abandoned` flag would have been ambiguous with the existing state field. A new `MessageState` value would have violated ADR-008's separation between logical message lifecycle and delivery work status. Adding `ABANDONED` to `OutboxState` cleanly extends the delivery work enum without touching `MessageState` or introducing a parallel boolean dimension.

This decision was formalized in **ADR-009 (Bounded Delivery Retry and Abandonment)**. The consequence was that `MessageState` remained untouched, all Phase 4 lifecycle tests continued to pass without modification, and the retry manager gained a clean terminal state to reason about.

#### Design Decision: Per-Entry Attempt Counter with Restart Persistence

The next question was where to store the retry attempt count. Three options were considered:

1. **Per-configuration global counter** (rejected — cannot handle multiple messages in flight independently).
2. **In-memory per-entry counter** (rejected — would reset to 0 on process restart, allowing the retry limit to be bypassed by simply restarting the application).
3. **Per-entry `attemptCount` field on `OutboxEntry`, persisted in SQLite** (chosen).

The chosen approach requires an additive schema evolution: `ALTER TABLE outbox ADD COLUMN attempt_count INTEGER NOT NULL DEFAULT 0`. This is safe against existing S5.3 databases because the `DEFAULT 0` clause ensures rows created before the migration acquire a valid initial value. The `try { ALTER TABLE ... } catch { ignored }` pattern in `SqliteDeliveryOutbox.initSchema()` makes the migration idempotent — repeated startups do not fail if the column already exists.

### 2.2 S5.5 — Delivery Attempt Observability

**Objective:** Expose delivery retry attempts to application-layer consumers (future UI, logging, analytics) as observable events, without introducing polling, without allowing observers to alter delivery semantics, and without allowing observer bugs to crash the reliability layer.

#### Design Decision: Passive Immutable Event with Isolation Guarantee

Three architectural constraints shaped this sprint:

1. **No polling.** The reliability layer is event-driven by design (peer JOIN events). Introducing a `ScheduledExecutorService` or a `while(true) poll(); sleep()` loop would violate this principle and consume battery on mobile deployments.
2. **Observers cannot alter delivery.** The observer must not be able to inject state changes, cancel retries, or influence which entries are dispatched. A `Consumer<RetryAttemptEvent>` return-void functional interface enforces this at the type system level.
3. **Observer failures must be isolated.** A misbehaving observer that throws a `RuntimeException` — for example, a UI listener with a null pointer bug — must not disrupt delivery processing for the current entry, subsequent entries in the same sweep, or delivery of unrelated messages.

The chosen model is a small immutable event value class (`RetryAttemptEvent`) and a functional listener interface (`RetryAttemptListener`), with all listener invocations wrapped in individual `try/catch(Exception)` blocks inside `DeliveryRetryManager.notifyListeners()`. A logging warning is emitted for any suppressed exception, but the delivery path continues uninterrupted.

The `RetryAttemptEvent.Outcome` enum has three values that map cleanly to the delivery lifecycle:

- **`DISPATCHED`** — The retry message was successfully written to the transport (does not imply ACK).
- **`FAILED`** — The retry attempt failed but the entry remains `PENDING` for future retry.
- **`ABANDONED`** — The retry failed and the attempt count reached `maxAttempts`, transitioning the entry to `OutboxState.ABANDONED`.

Note that `ACK-received-and-COMPLETED` is deliberately not part of this event stream in S5.5 — ACK correlation is handled inside `DefaultApplicationMessagingService.handleInboundAck`, and application consumers can observe delivery completion via the existing `MessageLifecycleListener.onStateChanged(messageId, MessageState.DELIVERED)` mechanism from Phase 4. Duplicating that signal in the retry observability layer would create two overlapping channels for the same information.

#### Design Decision: Ephemeral vs. Persistent Events

The S5.5 brief explicitly asked whether attempt events should be persisted. The choice was **ephemeral**: `RetryAttemptEvent` instances are constructed at the moment of dispatch, delivered synchronously to listeners, and not stored anywhere. The rationale:

1. **The two things that must persist already do.** `attemptCount` is persisted on `OutboxEntry` (S5.4), and terminal `ABANDONED` state is persisted on the outbox row. Historical attempt count and final outcome are recoverable after restart from the outbox itself.
2. **Persistent event storage would require a new schema, new indices, and new pruning policy.** None of these were justified by S5.5 acceptance criteria.
3. **Application consumers that want persistent logs can register a listener that writes to their own persistence.** The observability contract does not preclude this.

If a future sprint requires historical replay of retry attempts (e.g., for support/debugging tooling), a persistent event log can be added additively without breaking the S5.5 API.

### 2.3 S5.6 — Reliable Group Delivery

**Objective:** Extend the reliability guarantees from single-recipient direct messages to multi-recipient group messages, where each participant has independent delivery state and independent retry, and where completed recipients are never resent when other recipients later reconnect.

#### Design Decision: Parallel Abstraction, Not Extension

The single most important architectural decision in this sprint was **not** to overload the existing `DeliveryOutbox` interface with multi-recipient semantics. Two options were considered:

1. **Extend `DeliveryOutbox` with a list-of-recipients field on `OutboxEntry`.** Rejected. This would break the clean single-recipient model, force every existing single-peer method to handle both cases, and complicate the SQLite schema with either a delimited-string field or a join table. Every existing test using `OutboxEntry.pending(messageId, peer, conversationId)` would need to be reconsidered.

2. **Introduce a new parallel abstraction `GroupDeliveryOutbox` with composite key `(messageId, PeerId)`.** Chosen. The existing `DeliveryOutbox` remains untouched. Group delivery gets its own contract, its own storage table, and its own retry semantics. Both outboxes are managed by the same `DeliveryRetryManager` and swept in the same reconnection event, but their internal models are independent.

This decision was formalized in **ADR-010 (Per-Recipient Reliable Group Delivery)**. The consequence was that every existing S5.1–S5.5 test continued to pass without modification, and the group reliability implementation could be reasoned about in isolation from single-peer delivery.

#### Design Decision: Reuse `OutboxState`, Not a New Enum

Per-recipient states also need `PENDING`, `COMPLETED`, and `ABANDONED` — the same lifecycle as single-peer delivery. Rather than introducing a `GroupRecipientState` enum with identical semantics, `OutboxState` is reused directly. This keeps the reliability layer's vocabulary consistent and allows the same `Outcome` values in `RetryAttemptEvent` to describe both direct and group retry outcomes.

#### Design Decision: ACK Correlation via Sender Identity

Group ACK correlation required careful analysis. The existing S5.3 ACK flow correlates ACKs to outbox entries by `messageId` alone, because for single-recipient delivery there is exactly one recipient per `messageId`. For group messages, the same `messageId` has multiple recipients, so `messageId` alone is insufficient — the ACK must also identify which recipient is acknowledging.

Fortunately, the existing wire protocol already carries the sender identity in every `Message` frame's `senderId` field. When `handleInboundAck` fires, `senderPeerIdStr` is the ACKing peer's ID. The updated logic in `DefaultApplicationMessagingService.handleInboundAck` therefore:

1. First checks the direct outbox: if `findByMessageId(ackedMessageId)` returns an entry, this is a direct-message ACK; call `outbox.markCompleted(ackedMessageId)` and transition to `DELIVERED`.
2. Otherwise, treats it as a group ACK: call `groupOutbox.markRecipientCompleted(ackedMessageId, senderPeerId)`.
3. After marking the group recipient completed, check `groupOutbox.allRecipientsCompleted(ackedMessageId)`. If true, transition the logical message to `MessageState.DELIVERED`.

Critical semantics: the `MessageState.DELIVERED` transition for a group message now means "all intended recipients have acknowledged" rather than "the message was routed successfully." This is a stronger, more useful guarantee. Partial acknowledgment (some recipients completed, others still pending) leaves `MessageState` at `SENT`, correctly reflecting that delivery work is not yet fully complete.

**No wire protocol change was required.** The existing ACK frame `[0x02][messageId]` carries all necessary information because the sender identity is already part of the protocol envelope.

## 4. Wire Format & Protocol Compatibility

**No wire format changes were made in the Phase 5 extension.** The application-level framing bytes (`0x01 CHAT`, `0x02 ACK`, `0x03 GROUP_CHAT`) established in Phase 4 remain unchanged. Retried direct messages use the identical wire encoding as their original send. Retried group messages use the identical S4.5 group-frame encoding. Group ACKs use the identical S4.3 ACK encoding — the sender identity that enables per-recipient correlation was already present in the protocol envelope's `senderId` field.

A pre-S5.4 client running against a post-S5.6 client will interoperate correctly. From the receiving peer's perspective, a retried message is indistinguishable from a fresh send. An ACK from a group participant on an older client contains the same `messageId` and `senderId` fields that the S5.6 correlation logic uses, so partial group delivery works transparently across mixed-version deployments.

## 5. Persistence Model (End of Phase 5 Extension)

Three independent SQLite tables (deployable in one shared database or three separate databases) are now involved in each node:

| Store | Purpose | Table | Key Guarantee |
|---|---|---|---|
| `SqliteMessageHistoryStore` | "What messages do I know about?" | `messages` | Durable record of every message ever sent or received. |
| `SqliteDeliveryOutbox` | "Which direct messages still need delivery work?" | `outbox` | Durable queue of pending single-peer delivery intents with attempt counting. |
| `SqliteGroupDeliveryOutbox` | "Which group message recipients still need delivery work?" | `group_outbox` | Durable queue of per-recipient delivery intents with attempt counting. |

None of the three stores contains any transport metadata. No connection IDs, no socket references, no IP addresses, no ports. All destination identities are `PeerId.value()`.

The three stores are logically independent and can be opened with independent `Path` arguments, or optionally against the same JDBC `Connection` if the deployer wishes to unify them into a single database file. This mirrors the flexibility pattern established for `SqliteMessageHistoryStore` and `SqliteDeliveryOutbox` in S5.2.

## 6. Retry Policy (End of Phase 5 Extension Formal Documentation)

The Phase 5 extension retry policy consolidates and extends the S5.3 policy:

- **Trigger:** A retry sweep for peer P is initiated when P transitions through a successful `JOIN` handshake, causing `ProtocolListener.onPeerJoined(P)` to fire. Unchanged from S5.3.
- **Scope per trigger:** The retry manager performs two sweeps: (1) direct-message pending entries for peer P in FIFO order, (2) group-message pending recipient entries where recipient equals P.
- **Per-entry attempt tracking:** Every retry attempt increments the entry's `attemptCount` before dispatch. This applies uniformly to direct entries (via `DeliveryOutbox.updateAttemptCount`) and group recipient entries (via `GroupDeliveryOutbox.incrementAttemptCount`).
- **On success (transport dispatch):** The message transitions to `MessageState.SENT` via the delivery attempt callback. The outbox entry remains `PENDING` until an ACK arrives; then it becomes `COMPLETED`. `RetryAttemptEvent.Outcome.DISPATCHED` fires.
- **On failure below threshold:** The entry remains `PENDING`, so the next reconnection event will trigger another retry. `MessageState` transitions to `FAILED` (unchanged), and `RetryAttemptEvent.Outcome.FAILED` fires.
- **On failure at or above threshold:** The entry transitions to `OutboxState.ABANDONED`. Subsequent reconnection sweeps exclude the entry from `findPendingForPeer` / `findPendingMessageIdsForPeer`. `MessageState` transitions to `FAILED` for the final failed attempt, and `RetryAttemptEvent.Outcome.ABANDONED` fires. The abandoned entry remains queryable via `findByMessageId` for inspection but will never be automatically retried again.
- **Maximum attempts:** Configurable via `DeliveryRetryManager` constructor. Default: 3. Minimum: 1. Enforced with `IllegalArgumentException` at construction time.
- **Backoff:** None. Retries are immediate upon `onPeerJoined`. The event-driven trigger and bounded attempt count together prevent retry storms.
- **Group message completion:** A group message's logical `MessageState.DELIVERED` fires only when `groupOutbox.allRecipientsCompleted(messageId)` returns `true`. Partial completion (some recipients acknowledged, others still pending or abandoned) leaves the message at `SENT` or `FAILED` depending on immediate-dispatch outcome.
- **Duplicate protection:** The `messageId` is never regenerated. Recipients continue to deduplicate on `messageId` via `historyStore.save()`.

## 7. Final Acceptance Scenario (End-to-End Verification)

The following partial-delivery-and-reconnect scenario is fully validated by `GroupReliabilityIntegrationTest.testOnlyPendingRecipientIsRetriedOnReconnect`:

```text
1. Alice creates a group "pravah-core" with participants {Bob, Charlie}
   Alice.sendGroupMessage("Team Update")
   → History store: message saved (CREATED → SENT)
   → Group outbox: two entries enqueued (M1→Bob PENDING, M1→Charlie PENDING)
   → Immediate dispatch: Bob succeeds (transport.send OK), Charlie fails (offline)

2. Bob's ACK arrives at Alice
   → handleInboundAck: senderId is Bob
   → Direct outbox: no entry (M1 is not in direct outbox)
   → Group outbox: markRecipientCompleted(M1, Bob)
   → State check: allRecipientsCompleted(M1) is false (Charlie still PENDING)
   → MessageState remains SENT

3. Charlie reconnects
   → Coordinator fires onPeerJoined("charlie")
   → retryManager.retryPendingForPeer(charlie) executes
   → Direct outbox sweep: no entries for Charlie
   → Group outbox sweep: findPendingMessageIdsForPeer(charlie) returns [M1]
   → For M1: incrementAttemptCount(M1, Charlie) → 1
   → Reconstruct wire payload with S4.5 group frame [0x03][groupIdLen][groupId][content]
   → peerRouter.send(charlie, protocolMessage) with original messageId M1
   → Dispatched. RetryAttemptEvent.Outcome.DISPATCHED emitted.

4. IMPORTANT: Bob is NOT resent M1
   → Verified by transport tracking: sentMessagesByDest contains "conn-charlie" but NOT "conn-bob"
   → This proves the completed-recipient-never-resent invariant.

5. Charlie processes M1
   → handleInboundGroupChat: parses group frame, saves to history, notifies listeners, sends ACK

6. Charlie's ACK arrives at Alice
   → handleInboundAck: senderId is Charlie
   → Group outbox: markRecipientCompleted(M1, Charlie)
   → State check: allRecipientsCompleted(M1) is now true (both Bob and Charlie COMPLETED)
   → MessageState transitions to DELIVERED

7. Final state:
   → Group outbox: M1→Bob COMPLETED, M1→Charlie COMPLETED
   → allRecipientsCompleted(M1) = true
   → MessageState(M1) = DELIVERED
   → Total dispatches: Bob (1 immediate), Charlie (1 retry after reconnect)
   → Zero duplicate dispatches to Bob
   → Same messageId M1 throughout
```

Total elapsed messageId lineage for group message M1: **one messageId, one message, multiple independent per-recipient delivery attempts, zero synthetic retry IDs, zero duplicate sends to completed recipients**.

## 8. ADRs Produced (Phase 5 Extension)

- **ADR-009: Bounded Delivery Retry and Abandonment** — Documents the introduction of the `ABANDONED` outbox state, per-entry attempt counting persisted in SQLite, and the configurable `maxAttempts` parameter on `DeliveryRetryManager`. Justifies the choice not to overload `MessageState` and the choice to persist attempt counts durably rather than in memory.
- **ADR-010: Per-Recipient Reliable Group Delivery** — Documents the introduction of `GroupDeliveryOutbox` as a parallel abstraction to `DeliveryOutbox` rather than an extension of it, keyed by composite `(messageId, PeerId)`. Justifies why this preserves the clean single-recipient model, why `OutboxState` is reused rather than duplicated, and how ACK correlation works without any wire protocol change.

Both ADRs explicitly identify their scope, alternatives considered, persistence implications, and compatibility guarantees.

## 10. Explicitly Out of Scope

The following were **not** built in the Phase 5 extension, in strict adherence to the brief's scope discipline:

- Bluetooth, QUIC, or any non-TCP transport.
- Multi-path or adaptive routing.
- Transport switching or fallback.
- Encryption or authentication beyond what Phase 3 provided.
- Cloud relay, federation, or distributed brokering.
- Message synchronization or conflict resolution between multiple devices per peer.
- Push notifications or wake-on-message.
- Any UI, chat client, or Android integration.
- Exponential backoff or adaptive retry timing.
- Manual re-queue API for abandoned entries.
- Persistent event log for retry observability events.
- Multi-transport reliability triggers (currently reactive only to `onPeerJoined` from the single TCP transport).
- Group-level aggregate state derivation beyond the binary "all completed vs. not."
- Per-recipient read receipts distinct from delivery acknowledgment.
- Retry policy per-message-type or per-conversation.

These are correctly deferred to future phases.

## 12. Recommendation for Phase 6

Phase 5 (including this extension) now delivers a complete, tested, and architecturally clean reliability layer covering single-recipient and multi-recipient delivery with bounded retry, durable persistence, and passive observability. Natural next steps, in order of architectural priority:

1. **Multi-transport reliability trigger.** The current retry trigger fires only on `ProtocolListener.onPeerJoined` from the TCP transport. When Bluetooth, LAN, or Internet transports are added in later phases, the retry manager itself is transport-agnostic (it operates on `PeerId`), but the join-event source needs to be unified. This is an event-plumbing concern in the `PeerConnectionCoordinator` and does not require reliability-layer changes.

2. **Encryption at the application-message boundary.** Currently, `ApplicationMessage.content` is transmitted as plaintext bytes over the wire. Introducing per-conversation symmetric encryption would be an application-messaging-layer concern that does not affect reliability semantics — encrypted messages retry and ACK correlate identically to plaintext.

3. **Bounded retry with exponential backoff and jitter.** The current bounded policy retries immediately on every reconnect event. A future sprint could introduce a per-entry `nextRetryAt` timestamp and a scheduled sweep, but only if telemetry from real deployments proves it necessary. Premature introduction of backoff complexity is a known anti-pattern.

4. **Manual re-queue API for abandoned entries.** Application layers may wish to explicitly reset an abandoned entry to `PENDING` (for example, after user intervention or after network diagnostics). A `DeliveryOutbox.resetToPending(messageId)` method with matching `MessageState` transition would be a small additive change.

5. **Read receipts distinct from delivery receipts.** The current ACK signals "the receiving peer's messaging service accepted the message." A future extension could add a second application-layer signal for "the user actually saw the message in the UI." This would require a new application-payload type byte (e.g., `0x04 READ`) and matching wire-level logic, and warrants its own ADR.

None of these are urgent. The Phase 5 extension delivers a complete, production-ready reliability layer for the current single-transport TCP scenario with both direct and group messaging.
