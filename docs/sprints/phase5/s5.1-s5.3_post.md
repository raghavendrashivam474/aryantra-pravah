## 2. Sprint Deliverables

### 2.1 S5.1 — Delivery Intent & Outbox

**Objective:** Introduce the concept that the application *intends* to deliver a message, and ensure that this intent survives the immediate routing attempt. Previously, if `PeerRouter.send()` failed because the destination peer was unregistered, the message transitioned to `MessageState.FAILED` and the delivery intent was permanently lost.

#### Design Decision: Separate State Model

Before writing any implementation code, the architectural question was analyzed: *should `PENDING` be added to `MessageState`, or should delivery work tracking be a separate concern?*

The Phase 4 `MessageState` enum (`CREATED`, `SENT`, `DELIVERED`, `FAILED`) represents the logical lifecycle of a message from the application's perspective. Adding `PENDING` would conflate two orthogonal dimensions:

1. **Logical lifecycle:** What is the application-level status of this message?
2. **Delivery work status:** Does this message still need routing effort?

A message can legitimately be `FAILED` in its logical lifecycle (immediate routing did not succeed) while simultaneously being `PENDING` in the delivery work queue (retry will be attempted upon reconnection). A single enum cannot express both dimensions simultaneously.

This decision was formalized in **ADR-008 (Delivery Outbox State Separation)**. The consequence was that `MessageState` remained untouched, and all 230 Phase 4 lifecycle tests continued to pass without modification.

#### Files Added

**Source (`src/main/java/com/aryntra/pravah/messaging/reliability/`):**

- **`OutboxState.java`** — A dedicated two-state enum (`PENDING`, `COMPLETED`) representing delivery work status. Deliberately minimal: no `IN_FLIGHT`, `RETRYING`, or `FAILED` states, because these were not required by the S5.1 acceptance criteria. Additional states can be introduced later without breaking the contract.

- **`OutboxEntry.java`** — An immutable value object capturing a single unit of delivery work. Fields: `messageId`, `destination` (as `PeerId`), `conversationId`, `state`, `createdAt`. Equality is based on `messageId` alone, matching the identity semantics of `ApplicationMessage`. State transitions are performed via `withState(newState)`, which returns a new instance rather than mutating the original. The destination is stored as `PeerId`, never as `connectionId`, socket, or IP address — this is a hard architectural rule.

- **`DeliveryOutbox.java`** — The abstraction contract. Six operations: `enqueue`, `findPending`, `findPendingForPeer`, `findByMessageId`, `markCompleted`, `remove`. The interface makes no assumption about storage technology. The messaging layer depends only on this abstraction.

- **`InMemoryDeliveryOutbox.java`** — Thread-safe reference implementation backed by `ConcurrentHashMap`. Deterministic ordering is guaranteed via an internal `AtomicLong` sequence counter that serves as a tie-breaker when multiple entries share identical `Instant` timestamps (a real risk on fast local exchanges). The comparator sorts first by `createdAt`, then by sequence number.

#### Files Modified

- **`DefaultApplicationMessagingService.java`** — Three additive changes:
  1. New constructor accepting an optional `DeliveryOutbox` parameter. Default constructor creates an `InMemoryDeliveryOutbox`, preserving backward compatibility for all existing callers.
  2. `send()` now enqueues a `PENDING` outbox entry before attempting to route via `PeerRouter.send()`. If routing fails, `MessageState` transitions to `FAILED` but the outbox entry remains `PENDING`, preserving the delivery intent.
  3. `handleInboundAck()` now calls `outbox.markCompleted(messageId)` upon receiving an application-level ACK, closing the delivery work loop.

No changes to `ApplicationMessage`, `MessageState`, `ConversationId`, `PeerId`, `PeerRouter`, `PeerConnectionCoordinator`, or any Phase 3/4 contract.

#### Tests Added (S5.1)

- **`OutboxEntryTest`** — 9 tests covering validation (null messageId, blank messageId, null destination, null conversationId, null state, null createdAt) and behavior (`pending()` factory, `withState()` immutability, equality by messageId).
- **`InMemoryDeliveryOutboxTest`** — 7 tests covering enqueue/findPending, duplicate rejection, deterministic ordering with sequence tie-breaker, peer isolation via `findPendingForPeer`, markCompleted excludes from pending, remove behavior, and no-op removal of non-existent entries.
- **`DeliveryIntentIntegrationTest`** — 2 tests proving that a message sent to an unavailable peer results in `MessageState.FAILED` but the delivery intent survives in the outbox as `OutboxState.PENDING`, and that destination identity in the outbox is `PeerId`, never `connectionId`.

### 2.2 S5.2 — Offline Queue

**Objective:** Make the delivery outbox durable across process restarts. A message queued while Bob is offline must survive Alice's application shutting down and restarting.

#### Design Decision: Same Database, Separate Table

The question was whether to reuse the existing `SqliteMessageHistoryStore` database file or create a separate outbox database. The chosen approach was: **separate table, same database convention**, but with the flexibility for callers to use separate files if they wish.

The `SqliteDeliveryOutbox` constructor accepts either a `Path` (owns its own connection) or an existing `Connection` (shares with the history store). This mirrors the `SqliteMessageHistoryStore` constructor pattern from Phase 4 and preserves the option to unify or separate databases at the deployment level.

The schema is deliberately minimal — no retry metadata, no attempt counters, no backoff timers. Those concerns belong to S5.3 and can be added additively later without breaking the S5.2 schema.

#### Files Added

**Source (`src/main/java/com/aryntra/pravah/messaging/reliability/`):**

- **`SqliteDeliveryOutbox.java`** — Durable SQLite-backed implementation of `DeliveryOutbox`. Implements `AutoCloseable` for deterministic resource cleanup. Uses `synchronized` methods for thread-safe database access. Schema:

```sql
CREATE TABLE IF NOT EXISTS outbox (
    seq INTEGER PRIMARY KEY AUTOINCREMENT,
    message_id TEXT NOT NULL UNIQUE,
    destination_peer_id TEXT NOT NULL,
    conversation_id TEXT NOT NULL,
    status TEXT NOT NULL,
    created_at_epoch_ms INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_outbox_status_seq ON outbox(status, seq);
CREATE INDEX IF NOT EXISTS idx_outbox_peer_status_seq ON outbox(destination_peer_id, status, seq);
```

Ordering is guaranteed by `seq` (SQLite autoincrement), matching the deterministic FIFO ordering of the in-memory implementation. Duplicate `message_id` insertion is caught at the SQLite `UNIQUE` constraint level and translated to `IllegalArgumentException`, matching the in-memory contract exactly.

The `destination_peer_id` column stores `PeerId.value()` — no socket, no port, no connection reference. This preserves the architectural rule that reliability tracking is scoped by logical peer identity, never by ephemeral transport state.

#### Tests Added (S5.2)

- **`SqliteDeliveryOutboxTest`** — 7 tests across three nested groups:
  - *BasicOperations*: enqueue and findPending, duplicate rejection, markCompleted, remove.
  - *OrderingAndFiltering*: deterministic ordering by seq ASC, peer isolation.
  - *DurabilityAndRestart*: pending messages survive outbox close and reopen, completed entries also persist in their COMPLETED state.

- **`OfflineQueueDurabilityIntegrationTest`** — 1 integration test simulating the full S5.2 acceptance scenario. Alice queues two messages to Bob while Bob is offline. Alice's node shuts down completely (transport stopped, database connection closed, all in-memory state released). Alice restarts with the same database paths. The test verifies that both pending deliveries are still present in the outbox in the correct deterministic order, and that the history store also preserved the messages.

**S5.2 test delta: +8 tests. Total: 256.**

### 2.3 S5.3 — Retry & Reconnection

**Objective:** Automatically retry pending outbox messages when the destination peer reconnects. This closes the reliability loop: send offline → queue survives → peer reconnects → retry → ACK → DELIVERED.

#### Design Decision: Event-Driven, Not Polled

The reliability layer must not poll the network or the peer registry continuously. The Phase 3 substrate already emits a clean event when a peer completes its logical session handshake: `ProtocolListener.onPeerJoined(peerIdStr, message)`. This is fired by `PeerConnectionCoordinator` after a peer sends a valid `JOIN` message and is authenticated.

`DefaultApplicationMessagingService` already installs a `ProtocolListener` on the coordinator (for handling inbound `MESSAGE` frames). The S5.3 change extends the existing `onPeerJoined` callback to also trigger a retry sweep for that peer via `DeliveryRetryManager.retryPendingForPeer(peerId)`.

This decision has three important properties:

1. **No new polling threads or scheduled executors.** The retry mechanism is entirely reactive to existing peer lifecycle events.
2. **No modification to the Phase 3 protocol layer.** The `ProtocolListener` contract is reused as-is.
3. **Conservative retry policy for the first version.** One retry attempt per reconnection event. No exponential backoff, no retry counter, no maximum attempts. If the retry fails, the message remains `PENDING` and will be retried the next time the peer connects. This matches the S5.3 brief directive: *"prefer a conservative policy... do not implement exponential backoff unless it is actually required."*

#### Design Decision: Identity Invariance

The most critical rule in S5.3 is that a **retry is not a new message**. When `DeliveryRetryManager` retries a pending entry, it:

1. Reads the original `ApplicationMessage` from `MessageHistoryStore` using the original `messageId`.
2. Reconstructs the wire-level `Message` envelope with the **exact same** `messageId`.
3. Sends via `PeerRouter.send()`.

The `messageId` is never regenerated. There is no `msg-retry-1` or `msg-attempt-2` synthetic identity. This preserves end-to-end ACK correlation: when Bob receives the retried message and replies with an application ACK containing the original `messageId`, Alice's `handleInboundAck()` correctly transitions the original message to `DELIVERED` and marks the outbox entry `COMPLETED`.

#### Files Added

**Source (`src/main/java/com/aryntra/pravah/messaging/reliability/`):**

- **`DeliveryRetryManager.java`** — A small, focused component with one responsibility: retry pending outbox entries for a given peer. Constructor dependencies: `localPeerId`, `DeliveryOutbox`, `MessageHistoryStore`, `PeerRouter`, and a `BiConsumer<String, Boolean>` callback for reporting per-message attempt outcomes back to the messaging service. The retry method is `synchronized` to prevent concurrent retry sweeps for the same peer.

The retry manager does not directly update `MessageState`. Instead, it invokes the callback with the messageId and a success flag, letting the messaging service perform the state transition through its existing `updateState()` method. This keeps state management centralized in `DefaultApplicationMessagingService` and prevents the retry manager from acquiring knowledge about lifecycle listeners or history store update mechanics.

#### Files Modified

- **`DefaultApplicationMessagingService.java`** — Two additive changes:
  1. Constructor now instantiates a `DeliveryRetryManager` and passes it a callback that maps success → `MessageState.SENT` and failure → `MessageState.FAILED`.
  2. The `ProtocolListener.onPeerJoined()` implementation now calls `retryManager.retryPendingForPeer(joinedPeer)`. This is the single line that closes the reactive loop.

A public accessor `getRetryManager()` was added for test observability, matching the existing pattern (`getHistoryStore()`, `getOutbox()`, `getConversationManager()`).

#### Tests Added (S5.3)

- **`ReconnectAndRetryIntegrationTest`** — 2 end-to-end integration tests using real `TcpTransport` instances, real `PeerConnectionCoordinator` handshakes, and real `SqliteDeliveryOutbox` persistence:

  1. **`queuedMessageDeliveredOnReconnection`** — Alice sends to offline Bob (fails, but queued). Bob comes online. Bidirectional TCP connection is established and both peers exchange `JOIN` messages. Alice's `onPeerJoined("bob")` callback fires, which triggers `retryManager.retryPendingForPeer(bob)`. Bob receives the message with the **original** `messageId`, sends an ACK, Alice transitions to `DELIVERED`, and the outbox entry is `COMPLETED`.

  2. **`queuedMessagesSurviveRestartAndDeliver`** — Combines S5.2 durability with S5.3 retry. Alice queues a message to offline Bob, then Alice's node shuts down completely (transport stopped, databases closed). Alice restarts with the same database files. The outbox is verified to still contain the pending entry loaded from disk. Bob then comes online, the handshake completes, Alice's retry manager fires, and the message delivers successfully with the exact same `messageId` from before the restart.

**S5.3 test delta: +2 tests. Total: 258.**

## 4. Wire Format & Protocol Compatibility

**No wire format changes were made.** The application-level framing bytes (`0x01 CHAT`, `0x02 ACK`, `0x03 GROUP_CHAT`) established in Phase 4 remain unchanged. Retried messages use the identical wire encoding as originally-sent messages. A Phase 4 client that predates Phase 5 can interoperate with a Phase 5 client without any protocol negotiation, because from the peer's perspective a retried message is indistinguishable from a fresh send — it is simply a `MESSAGE` frame with a `messageId` the peer has not seen before.

## 5. Persistence Model

Two independent SQLite databases (or optionally a shared one) are now involved in Alice's node:

| Store | Purpose | Table | Key Guarantee |
|---|---|---|---|
| `SqliteMessageHistoryStore` | "What messages do I know about?" | `messages` | Durable record of every message ever sent or received. |
| `SqliteDeliveryOutbox` | "Which messages still need delivery work?" | `outbox` | Durable queue of pending delivery intents. |

A message can exist in both simultaneously: for example, an outbound message that was queued while the peer was offline exists in `messages` (state `FAILED` initially, then `DELIVERED` after ACK) and in `outbox` (state `PENDING` initially, then `COMPLETED` after ACK). Once delivered, the history record persists forever while the outbox entry is marked completed and could optionally be pruned in a future sprint.

Neither store contains any transport metadata. No connection IDs, no socket references, no IP addresses, no ports. All destination identities are stored as `PeerId.value()`.

## 6. Retry Policy (S5.3 Formal Documentation)

The Phase 5 retry policy is deliberately conservative:

- **Trigger:** A retry attempt for peer P is initiated only when P transitions through a successful `JOIN` handshake, causing `ProtocolListener.onPeerJoined(P)` to fire.
- **Scope per trigger:** One attempt per pending outbox entry for peer P, in strict FIFO order (`seq ASC`).
- **On success:** The message transitions to `MessageState.SENT`. The outbox entry remains `PENDING` until an ACK arrives; then it becomes `COMPLETED`.
- **On failure:** The message remains recoverable. `MessageState` transitions to `FAILED`, but the outbox entry remains `PENDING`, so the next reconnection event will trigger another retry.
- **Maximum attempts:** Unbounded. There is no attempt counter and no give-up condition in the current implementation. This is intentional and matches the S5.3 brief. A future sprint may introduce a bounded retry policy with dead-letter semantics, but this would be an additive extension, not a breaking change.
- **Backoff:** None. The retry is immediate upon `onPeerJoined`. Since the trigger is event-driven and not periodic, this cannot cause a retry storm — the number of retries is bounded by the number of reconnection events.
- **Duplicate protection:** The `messageId` is never regenerated. Bob's `handleInboundChat` deduplicates on `messageId` via the `historyStore.save()` call, which throws `IllegalArgumentException` on duplicate insertion (caught and logged at `FINE` level).

## 7. Final Acceptance Scenario (End-to-End Verification)

The following scenario was fully validated by `ReconnectAndRetryIntegrationTest.queuedMessagesSurviveRestartAndDeliver`:

```text
1. Alice.send(bob, "Persisted message across restart")
   → History store: message saved (CREATED → FAILED)
   → Outbox: entry enqueued (PENDING)
   → PeerRouter.send() throws (Bob not registered)
   → MessageState = FAILED, OutboxState = PENDING

2. Alice's node shuts down completely
   → SqliteMessageHistoryStore.close()
   → SqliteDeliveryOutbox.close()
   → TcpTransport.stop()
   → All in-memory state released

3. Alice restarts with the same database files
   → SqliteMessageHistoryStore reopens
   → SqliteDeliveryOutbox reopens
   → Outbox.findPendingForPeer(bob) returns the entry from disk

4. Bob starts up

5. TCP connection established
   → Alice.transport.connect(bob's address)
   → Alice sends JOIN to Bob → Bob's coordinator authenticates Alice
   → Bob sends JOIN to Alice → Alice's coordinator authenticates Bob
   → ProtocolListener.onPeerJoined("bob") fires on Alice's messaging service

6. DeliveryRetryManager.retryPendingForPeer(bob) executes
   → Reads original ApplicationMessage from history (same messageId)
   → Reconstructs wire Message with original messageId
   → PeerRouter.send(bob, message) succeeds
   → MessageState = SENT (via callback)

7. Bob receives the message
   → messageId matches original (identity invariance verified)
   → Content matches original
   → Bob's messaging service saves to history and sends ACK

8. Alice receives ACK
   → handleInboundAck(messageId) fires
   → MessageState = DELIVERED
   → Outbox.markCompleted(messageId)
   → OutboxState = COMPLETED

9. Alice.outbox.findPendingForPeer(bob) → empty
   Alice.outbox.findByMessageId(originalId).state() = COMPLETED
```

Total elapsed messageId lineage: **one messageId, one message, multiple delivery attempts**. Never a synthetic retry ID. Never a duplicate logical message.

## 12. Recommendation for Phase 6

Phase 5 establishes the reliability foundation. Natural next steps, in order of architectural priority:

1. **Bounded retry policy with dead-letter semantics.** Introduce optional attempt counters and a terminal `ABANDONED` state for entries that repeatedly fail across many reconnections. Would require additive schema evolution on the outbox table.

2. **Multi-transport reliability.** The current implementation assumes a single transport (`TcpTransport`). When Bluetooth or LAN discovery transports are added in later phases, the outbox and retry manager will work transparently — they are transport-agnostic — but the reconnection trigger will need to fire on any transport's peer-joined event.

3. **Group message reliability.** S4.5 group messaging currently uses best-effort fan-out. Extending the outbox model to track per-recipient delivery state would enable reliable group delivery. This is a substantial design decision and warrants its own ADR.

4. **Delivery attempt observability.** A `RetryAttemptListener` interface would allow the UI layer to display "delivering..." states, retry counts, and last-attempt timestamps without polling.

None of these are urgent. Phase 5 delivers a complete, tested, and architecturally clean reliability layer that is production-ready for the current single-transport TCP scenario.
