# Sprint S3.6 — End-to-End Peer Integration

## Objective

Wire Pravah's independently-built peer subsystems (Identity, Registry, Router, Discovery, Presence, Protocol, Transport) into a single cooperating pipeline so that two real nodes can automatically progress through the full peer lifecycle — LAN discovery → TCP connection → JOIN handshake → CONNECTED presence → bidirectional MESSAGE exchange → LEAVE → AVAILABLE → TTL expiry → UNAVAILABLE — without any manual orchestration or hardcoded bridging at the application layer.

## Existing Baseline

- S3.1–S3.5 complete and frozen on `v0.3.5` tag.
- 172/172 tests passing after a surgical fix to a pre-existing flaky assertion in `EndToEndProtocolIntegrationTest` (order-dependent concurrent message arrival).
- Subsystems existed as clean, isolated layers with no automatic cross-layer wiring:
  - `LanPeerDiscovery` → `PeerPresenceBridge` → `PeerRegistry` (discovery path)
  - `TcpTransport` → `FrameDecoder` → `ProtocolSessionManager` (protocol path)
  - `PeerRouter` → `PeerRegistry` → `Transport.send()` (outbound path)
- The critical gap: no mechanism linking `connectionId` (transport-level) to `PeerId` (logical identity), and no automatic presence transitions on TCP connect/disconnect.

## Implemented Capability

### 1. TransportListener Lifecycle Extension (ADR-004)

- **TransportListener** (`com.aryntra.pravah.transport.TransportListener`):
  - Added two `default` methods: `onConnectionOpened(String connectionId)` and `onConnectionClosed(String connectionId)`.
  - `@FunctionalInterface` preserved — existing lambda consumers implementing only `onDataReceived` remain 100% compatible with zero code changes.
  - Decision documented in `ADR-004-transport-connection-lifecycle.md`.

### 2. TcpTransport Lifecycle Notifications

- **TcpTransport** (`com.aryntra.pravah.transport.tcp.TcpTransport`):
  - `attachActiveSocket()`: fires `listener.onConnectionOpened(id)` after registering the connection in the internal map and starting the reader thread.
  - `closeConnection()`: fires `listener.onConnectionClosed(id)` when a connection is removed from the registry (covers remote close, local stop, and error-driven teardown).
  - Listener exceptions are caught and logged without killing transport threads.
  - All existing behavior (framing, reader threads, concurrent connection map, send semantics, connection lookup normalization) remains completely intact.

### 3. PeerConnectionCoordinator

- **PeerConnectionCoordinator** (`com.aryntra.pravah.peer.PeerConnectionCoordinator`):
  - Implements `TransportListener`, serving as the single integration point between transport, protocol, identity, and presence layers.
  - **Inbound frame demuxing**: Maintains a per-`connectionId` `FrameDecoder` map. Incoming raw bytes from `onDataReceived` are fed through the decoder, parsed via `MessageParser`, and dispatched to `handleInboundMessage`.
  - **JOIN handling** (identity handshake):
    1. Extracts `PeerId` from `message.senderId()` via `PeerId.of()`.
    2. Binds `connectionId ↔ PeerId` in bidirectional `ConcurrentHashMap`s.
    3. Notifies `PeerPresenceBridge.handlePeerConnected(peerId, connectionId)` — updating registry and transitioning presence to `CONNECTED`.
    4. Processes `sessionManager.processMessage(message)` — transitioning protocol state to `JOINED` and firing downstream `ProtocolListener.onPeerJoined`.
    - **Critical ordering**: Presence bridge is updated *before* session manager processing to guarantee that by the time any `ProtocolListener` callback fires, the peer is already `CONNECTED` in presence and registered with an active `connectionId`. This eliminates a race condition where listener threads could observe stale `AVAILABLE` state.
  - **LEAVE handling**:
    1. Unbinds `connectionId ↔ PeerId`.
    2. Notifies `PeerPresenceBridge.handlePeerDisconnected(peerId)` — nulling registry `connectionId`, transitioning presence to `AVAILABLE`.
    3. Processes `sessionManager.processMessage(message)` — transitioning protocol state to `LEFT`.
  - **MESSAGE handling**: Forwards directly to `sessionManager.processMessage()`.
  - **Connection drop** (`onConnectionClosed`):
    1. Removes per-connection `FrameDecoder`.
    2. Looks up `PeerId` for the closed `connectionId`.
    3. If found: unbinds mappings, notifies presence bridge (disconnected), resets protocol session.
  - **Protocol listener forwarding**: Wraps `ProtocolSessionManager`'s internal listener to forward `onPeerJoined`, `onMessageReceived`, `onPeerLeft` to an externally registered `ProtocolListener`.
  - **Query API**: `getPeerIdForConnection(connectionId)` and `getConnectionIdForPeer(peerId)` for bidirectional identity resolution.

### 4. Architectural Boundaries Preserved

The following invariants from the S3.6 brief were verified and maintained:

| Boundary | Status |
|----------|--------|
| Transport remains PeerId-agnostic | ✅ `TcpTransport` never references `PeerId` |
| Discovery remains separate from connection management | ✅ `LanPeerDiscovery` unchanged |
| Presence remains separate from protocol `PeerState` | ✅ `PeerPresenceState` ≠ `PeerState` |
| `PeerId` remains separate from `connectionId` | ✅ Mapped only in coordinator |
| No new identity handshake invented | ✅ JOIN is the sole identity mechanism |
| No existing contracts redesigned | ✅ Only `default` methods added to `TransportListener` |

## Architectural Decisions

- **ADR-004**: Transport connection lifecycle integration via `default` methods on `TransportListener`. Chosen over alternatives (separate `ConnectionLifecycleListener` interface, polling-based detection, or modifying `Transport` interface) because it preserves `@FunctionalInterface`, requires zero changes to existing consumers, and adds exactly two methods with no-op defaults.
- **Presence-before-protocol ordering**: `PeerPresenceBridge` is updated before `ProtocolSessionManager.processMessage()` in the coordinator. This guarantees that any `ProtocolListener` callback observes fully consistent state. The alternative (protocol-first) caused a race where listener threads could check presence before the coordinator thread completed the bridge update.
- **JOIN as sole identity handshake**: No new protocol message types (`HELLO`, `IDENTIFY`, etc.) were introduced. The existing `JOIN` message's `senderId` field serves as the logical identity binding. This avoids protocol version fragmentation and keeps the wire format stable.
- **Coordinator as thin glue**: `PeerConnectionCoordinator` owns no persistent state beyond the `connectionId ↔ PeerId` maps and per-connection `FrameDecoder` instances. All durable state lives in `PeerRegistry`, `PeerPresenceManager`, and `ProtocolSessionManager`. The coordinator is a routing layer, not a state machine.

## Out of Scope

- Bluetooth, Internet discovery, Internet transport, QUIC.
- Multi-transport routing, adaptive path selection, path switching.
- Retry, offline queue, delivery receipts, message history, persistence.
- Authentication, encryption, key exchange.
- Android, UI/chat screen, Aryntra Flux integration.
- Cloud services, accounts.
- Connection arbitration for simultaneous bidirectional TCP connects (documented as a known limitation; no connection storm observed in testing but no deterministic dedup policy implemented).

## Known Limitations

- **Simultaneous connection dedup**: If Alice and Bob both initiate TCP connections to each other simultaneously after mutual discovery, two connections may briefly coexist. The current implementation handles this gracefully (both JOINs succeed, last-write-wins on the mapping), but no explicit connection arbitration policy (e.g., "higher PeerId wins") is implemented. This is acceptable for the current LAN-only scope but should be addressed before multi-transport or Internet peering.
- **LanPeerDiscovery stop latency**: UDP socket teardown in `LanPeerDiscovery.stop()` takes 2–4 seconds due to executor shutdown. This is a pre-existing S3.4 characteristic, not introduced by S3.6, but it affects test timing for TTL-based assertions.
- **Single-transport assumption**: `PeerConnectionCoordinator` is bound to one `Transport` instance. Multi-transport coordination (e.g., LAN + Bluetooth) would require a higher-level orchestrator or a transport-agnostic connection abstraction.
- **No connection retry**: If a TCP connection drops, the coordinator cleans up state but does not attempt reconnection. Reconnection is an application-layer responsibility.
- **Presence is in-memory only**: No persistence across process restarts (inherited from S3.5).

## Next Steps

Phase 3's peer foundation is now genuinely end-to-end. The logical next architectural layers could include:

- **S3.7**: Connection arbitration and dedup policy for simultaneous bidirectional connects.
- **S3.8**: Heartbeat/keepalive protocol for active liveness probing (replacing passive TTL-only expiry).
- **S3.9**: Multi-transport abstraction (Bluetooth, Wi-Fi Direct) behind the existing `Transport` interface.
- **Phase 4**: Application-layer messaging (chat rooms, group presence, message history).

The integrated core is stable and ready to support any of these directions without foundational rework.
