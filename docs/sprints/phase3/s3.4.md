# Sprint S3.4 — LAN Peer Discovery

## Objective
Enable Pravah nodes on the same local network to automatically discover one another without manual peer identity entry, transitioning the system from "I can communicate with a peer if somebody tells me about that peer" to "Pravah can discover nearby Pravah peers autonomously."

## Existing Baseline
- S3.3 complete (PeerId, PeerRecord, PeerRegistry, PeerRouter operational, 121/121 tests passing).
- PeerRegistry supports `PeerRecord.disconnected(PeerId)` for known-but-unconnected peers.
- No discovery mechanism existed; all peer knowledge was manually injected.

## Implemented Capability
- **DiscoveryPacket** (com.aryntra.pravah.peer.discovery.DiscoveryPacket):
  - Dedicated wire format for LAN discovery, intentionally separate from the application Message format.
  - Layout: `[PRAH magic 4B][version 1B][id_len 2B][peer_id NB][tcp_port 2B]`.
  - Strict deserialization: rejects invalid magic, unsupported version, zero-length ID, truncated payloads.
  - Minimum packet size: 10 bytes.

- **DiscoveredPeer** (com.aryntra.pravah.peer.discovery.DiscoveredPeer):
  - Immutable record binding `PeerId` (WHO) to `hostAddress` + `port` (WHERE).
  - Reuses existing `PeerId` class; no parallel identity model introduced.

- **PeerDiscoveryListener** (com.aryntra.pravah.peer.discovery.PeerDiscoveryListener):
  - Functional interface for discovery event callbacks.

- **LanPeerDiscovery** (com.aryntra.pravah.peer.discovery.LanPeerDiscovery):
  - UDP broadcast-based LAN discovery engine using `255.255.255.255`.
  - Dual-thread architecture: daemon receiver thread (blocking `socket.receive()`) + scheduled broadcaster executor.
  - Pre-bind `SO_REUSEADDR` for multi-node coexistence on same host.
  - Self-exclusion: ignores own broadcasts by matching `PeerId`.
  - Idempotent lifecycle: repeated `start()`/`stop()` calls are safe no-ops.
  - Clean shutdown: socket closure breaks blocking receives, executor `shutdownNow()` with await.

## Architectural Decisions
- Discovery wire format is deliberately separate from the application `Message` wire format. Discovery traffic and chat messages have different responsibilities and lifecycles.
- UDP broadcast (`255.255.255.255`) chosen over multicast for maximum LAN compatibility without subnet calculation complexity.
- Discovery establishes *knowledge*, not *trust*. No authentication is performed on discovered peers.
- The `PeerId` in discovery packets is the same logical identity used throughout the peer subsystem. No `LanPeerId` or `DiscoveryPeerId` variants.
- Endpoint IP is derived from the UDP datagram source address, not embedded in the packet payload. The packet carries WHO (PeerId) + WHERE-port (TCP port) only.
- Discovery does not automatically establish TCP connections. It registers peers as `PeerRecord.disconnected(peerId)` in the registry.

## Out of Scope
- Peer authentication or identity verification.
- Multicast or mDNS-based discovery.
- Cross-subnet or internet discovery.
- Automatic TCP connection establishment upon discovery.
- Discovery over Bluetooth, QUIC, or any non-UDP transport.

## Known Limitations
- UDP broadcast does not cross router boundaries; discovery is limited to the local subnet.
- No discovery packet rate limiting or backpressure mechanism.
- Discovered peers are registered as disconnected; the bridge to active connection is deferred to S3.5.
- The `SO_REUSEADDR` pre-bind pattern allows multiple nodes on the same host but may behave differently across operating systems.
