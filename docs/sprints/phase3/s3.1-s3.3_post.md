**Author:** Implementation team

## Executive Summary

Phase 3 (S3.1–S3.3) successfully evolved Pravah from a protocol running over raw TCP connections into a communication system that addresses **logical peers** rather than transport-level connection identifiers.

The application layer can now express intent as:

```
router.send(PeerId.of("peer-b"), message);
```

without any knowledge of TCP connection IDs, socket addresses, IP addresses, or ports.

**All 87 Phase 2 baseline tests remain green. Total test count is now 121/121 passing.**

No existing Phase 0, 1, or 2 source files were modified. The entire peer subsystem was layered on top of the existing architecture.

---

## 1. Baseline & Constraints

At the start of Phase 3, the system had:

- A complete framing layer (`FrameEncoder` / `FrameDecoder`) operating over length-prefixed TCP streams with a 16 MB max frame size.
- A protocol layer (`MessageEncoder` / `MessageParser` / `ProtocolSessionManager`) handling JOIN, MESSAGE, and LEAVE semantics with deterministic state transitions.
- A transport abstraction (`Transport` interface) with a single TCP implementation (`TcpTransport`) supporting multiple concurrent connections identified by `socket.getRemoteSocketAddress().toString()`.
- Logical `senderId` on messages, but no formal peer identity model, no peer registry, and no peer-aware routing.

**Hard constraints enforced throughout:**

1. `Transport.java`, `TransportListener.java`, and `TcpTransport.java` must not be modified.
2. `Message.java` (immutable record) must not be mutated.
3. `FrameEncoder.java`, `FrameDecoder.java`, `MessageEncoder.java`, `MessageParser.java`, and `ProtocolSessionManager.java` are protected.
4. No authentication, encryption, persistence, or discovery was in scope.

## 2. S3.1 — Peer Identity

### What was built

A single class: `com.aryntra.pravah.peer.PeerId`.

`PeerId` is an immutable, final class with a private constructor and two factory methods:

- `PeerId.of(String value)` — creates an identity from an explicit string, with null/blank rejection and automatic whitespace trimming.
- `PeerId.generate()` — creates a random identity backed by `UUID.randomUUID()`.

Equality and hash code are value-based on the trimmed string. This means `PeerId.of("alice")` and `PeerId.of("  alice  ")` are equal, which is a deliberate normalization choice.

### Why this shape

The brief explicitly separated **identity representation** from **identity generation**. `PeerId` is the representation. Generation is a convenience method on the same class for now. If Phase 4 or 5 introduces cryptographic identity, a `PeerIdentityProvider` abstraction can be layered on top without changing `PeerId` itself.

### What was deliberately excluded

No certificates, no public/private keys, no persistent accounts, no database storage. The goal was purely: "give a peer a stable logical identifier inside the Pravah system."

### Tests

13 unit tests in `PeerIdTest` covering creation, null/blank rejection, trimming, equality, hash consistency, toString, generation validity, and generation uniqueness.

## 3. S3.2 — Peer Registry

### What was built

Two classes in `com.aryntra.pravah.peer`:

**`PeerRecord`** — an immutable Java record binding a `PeerId` to an optional transport `connectionId`:

```java
public record PeerRecord(PeerId peerId, String connectionId)
```

Key semantics:
- `connectionId` is nullable. A null connection ID means the peer is known but currently disconnected.
- Factory methods `connected(peerId, connId)` and `disconnected(peerId)` make intent explicit.
- `isConnected()` returns true only when `connectionId` is non-null and non-blank.
- `withConnectionId(newConnId)` returns a new record, preserving immutability.

**`PeerRegistry`** — a thread-safe in-memory store backed by `ConcurrentHashMap<PeerId, PeerRecord>`:

Key operations:
- `register(PeerRecord)` / `register(PeerId, String connectionId)` — stores or **replaces** an existing record.
- `lookup(PeerId)` — returns `Optional<PeerRecord>`.
- `lookupByConnectionId(String)` — reverse lookup, useful for mapping incoming transport events back to logical peers.
- `contains(PeerId)`, `remove(PeerId)`, `allPeers()`, `size()`, `clear()`.

### Critical design decision: duplicate registration

When a peer re-registers (e.g., reconnects on a new TCP socket), the registry **replaces** the old record rather than rejecting it. This was a deliberate choice because:

1. TCP connections are ephemeral. A peer reconnecting will have a new connection ID.
2. Rejecting duplicates would force the caller to explicitly remove-then-register, creating a race window.
3. Replace semantics are atomic under `ConcurrentHashMap.put()`.

This decision is documented in the sprint report and should be revisited if Phase 4 introduces multi-transport peers (where a single peer might have *multiple* simultaneous connections).

### Concurrency

The registry was validated under concurrent access with 8 threads × 500 operations each in `PeerRegistryTest.concurrentOperations()`. No locking beyond `ConcurrentHashMap`'s internal segmentation was needed.

### Tests

13 unit tests in `PeerRegistryTest` covering registration, lookup, reverse lookup, duplicate replacement, removal, unmodifiable collection views, record invariants, null handling, and concurrent stress.

## 4. S3.3 — Peer-to-Peer Routing

### What was built

Two classes in `com.aryntra.pravah.peer`:

**`PeerRoutingException`** — extends `PravahException`. Thrown when a message cannot be delivered to a logical peer. Covers three failure modes:
- Peer not registered.
- Peer registered but disconnected (no active connection ID).
- Underlying transport failure during dispatch.

**`PeerRouter`** — the central routing component. Constructor takes a `PeerRegistry` and a `Transport`:

```java
public PeerRouter(PeerRegistry registry, Transport transport)
```

Primary method:

```java
public void send(PeerId destination, Message message)
```

The internal pipeline is:

```
1. registry.lookup(destination) → PeerRecord
2. Verify PeerRecord.isConnected()
3. MessageEncoder.encode(message) → byte[]
4. FrameEncoder.encode(encoded) → byte[]
5. transport.send(connectionId, framedBytes)
```

A convenience overload exists for quick sends:

```java
public void send(PeerId sender, PeerId destination, String messageId, byte[] payload)
```

This constructs a `Message` of type `MESSAGE` internally.

### Critical architectural decision: Message is NOT mutated

The brief raised the question of whether `destination` should be added to the `Message` record. The decision was **no**. The `Message` record remains:

```java
public record Message(MessageType type, String senderId, String messageId, byte[] payload)
```

Destination is a **routing concern**, not a **message semantics concern**. The router receives the destination as a separate parameter and resolves it to a connection ID before dispatching. This keeps the wire protocol unchanged and avoids breaking all 87 existing tests.

### Critical architectural decision: Transport remains PeerId-agnostic

The `Transport` interface was not modified. It still operates on `String connectionId`:

```java
void send(String destinationId, byte[] payload);
```

The `PeerRouter` is the sole component that translates `PeerId → connectionId`. This preserves the clean layering:

```
Application → PeerRouter → PeerRegistry → Transport → TcpTransport → TCP
```

The transport layer has zero awareness of the peer model.

### Integration test

`PeerRoutingIntegrationTest` spins up three real `TcpTransport` instances:

- **Node A** (server) — owns a `PeerRegistry` and `PeerRouter`.
- **Node B** (client) — connects to A, announces itself as "peer-b" via a JOIN message.
- **Node C** (client) — connects to A, announces itself as "peer-c" via a JOIN message.

Node A's transport listener dynamically registers incoming peers by parsing their JOIN messages and mapping `senderId → connectionId` in the registry. Node A then sends messages to `PeerId.of("peer-b")` and `PeerId.of("peer-c")` through the router. Both messages arrive at the correct recipients with correct payloads.

The test verifies that:
- Node A never references TCP connection IDs, IP addresses, or ports when sending.
- Messages intended for B do not reach C and vice versa.
- The full encode → frame → transport → receive → deframe → parse pipeline works end-to-end through the peer routing layer.

### Tests

7 unit tests in `PeerRouterTest` (mock transport) + 1 integration test in `PeerRoutingIntegrationTest` (real TCP).

## 8. Known Limitations

1. **Single connection per peer.** The current `PeerRecord` holds exactly one `connectionId`. If Phase 4 introduces multi-transport (e.g., a peer reachable via both TCP and Bluetooth), `PeerRecord` will need to evolve to hold a collection of connection references.

2. **No offline queue.** Sending to a disconnected peer throws `PeerRoutingException`. There is no message buffering or retry. This is intentional for S3.3 but will need addressing before production use.

3. **No automatic peer registration.** The integration test manually wires `senderId → connectionId` in the registry upon receiving JOIN messages. In production, this mapping should be handled by a dedicated session/registration component, likely integrated with `ProtocolSessionManager`.

4. **No peer eviction.** The registry grows unbounded. There is no TTL, heartbeat-based expiry, or LRU eviction. Acceptable for S3.2 but needs a strategy before scaling.

5. **Identity is not authenticated.** `PeerId` is a plain string wrapper. Any node can claim any identity. Authentication is a future concern (Phase 5+).

## 9. What's Next: S3.4 — Peer Discovery

With the peer model now established, S3.4 (LAN Discovery) can populate the `PeerRegistry` automatically rather than requiring manual registration. The discovery subsystem should:

1. Broadcast/scan for peers on the local network.
2. Upon finding a peer, create a `PeerId` and register it in the `PeerRegistry`.
3. Establish a transport connection and update the `PeerRecord` with the active `connectionId`.
4. Feed naturally into the existing `PeerRouter` pipeline without any changes to S3.1–S3.3 code.

The key architectural benefit of doing S3.1–S3.3 first is that discovery now has a well-defined target to populate, rather than creating a parallel concept that would later need reconciliation.
