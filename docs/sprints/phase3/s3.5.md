# Sprint S3.5 — Peer Presence

## Objective
Introduce a first-class presence model answering "What is the current availability state of a known peer?" — cleanly separated from protocol session semantics (JOINED/LEFT) and from raw transport connection state. Enable applications to reason about peer availability without embedding TCP or discovery knowledge.

## Existing Baseline
- S3.4 complete (LanPeerDiscovery, DiscoveryPacket, DiscoveredPeer, PeerDiscoveryListener operational, 161/161 tests passing).
- PeerRegistry tracks known peers and their current `connectionId` (nullable).
- Protocol `PeerState` (JOINED/LEFT) exists but represents chat session semantics, not network availability.

## Implemented Capability
- **PeerPresenceState** (com.aryntra.pravah.peer.presence.PeerPresenceState):
  - Four-state enum: `UNKNOWN`, `AVAILABLE`, `CONNECTED`, `UNAVAILABLE`.
  - Deliberately distinct from protocol `PeerState`.

- **PeerPresence** (com.aryntra.pravah.peer.presence.PeerPresence):
  - Immutable record capturing `PeerId`, `state`, `hostAddress`, `port`, `lastSeen` (Instant).
  - Default `PeerPresence.unknown(peerId)` factory for queries on unknown peers.

- **PeerPresenceListener** (com.aryntra.pravah.peer.presence.PeerPresenceListener):
  - Functional interface delivering `onPresenceChanged(peerId, oldPresence, newPresence)`.

- **PeerPresenceManager** (com.aryntra.pravah.peer.presence.PeerPresenceManager):
  - Thread-safe presence coordinator backed by `ConcurrentHashMap.compute()` for atomic state transitions.
  - Three input events: `reportDiscovered(peerId, host, port)`, `reportConnected(peerId)`, `reportDisconnected(peerId)`.
  - Background TTL-based expiry scheduler: AVAILABLE peers whose `lastSeen` is older than TTL transition to UNAVAILABLE.
  - CONNECTED peers are never expired by the TTL check.
  - Idempotent lifecycle: repeated `start()`/`stop()` calls are safe.
  - Deduplication: listeners fire only on actual state changes, not on same-state updates.

- **PeerPresenceBridge** (com.aryntra.pravah.peer.presence.PeerPresenceBridge):
  - Implements `PeerDiscoveryListener`, integrating LAN discovery with the registry and presence manager.
  - `onPeerDiscovered(peer)`: updates presence to AVAILABLE, registers peer as disconnected in the registry if not already known.
  - `handlePeerConnected(peerId, connectionId)`: updates registry with active connectionId, transitions presence to CONNECTED.
  - `handlePeerDisconnected(peerId)`: nulls the registry connectionId, transitions presence to AVAILABLE (if within TTL) or UNAVAILABLE.

## Architectural Decisions
- Presence state is architecturally distinct from protocol session state. `PeerPresence` answers "is the peer reachable?" while protocol `PeerState` answers "is the peer part of the chat session?"
- The four presence states form a directed but not strictly linear graph. `AVAILABLE` and `CONNECTED` can both transition to each other; `UNAVAILABLE` can return to either upon fresh evidence.
- TTL expiry only affects `AVAILABLE` peers. `CONNECTED` peers cannot be evicted by silence because the active connection is stronger evidence than a discovery timestamp.
- Presence updates use `ConcurrentHashMap.compute()` for atomic read-modify-write, avoiding lock-based synchronization on the map itself.
- The bridge is a coordinator, not a rewriter. It never mutates records held by the registry; it only invokes registry `register()` calls.
- No retry, queue, or offline messaging behavior is introduced. Presence informs the application; it does not act on the application's behalf.

## Out of Scope
- Peer authentication or identity verification.
- Heartbeat protocol for active liveness probing.
- Offline message queueing, store-and-forward, or retry semantics.
- Multi-transport presence aggregation (e.g., "AVAILABLE via LAN, UNAVAILABLE via Internet").
- Application-driven presence hints beyond discovery and connection lifecycle events.

## Known Limitations
- Presence expiry granularity is `max(100ms, TTL/2)`; sub-100ms TTLs will not yield tighter eviction resolution.
- The bridge assumes the caller (application or session manager) invokes `handlePeerConnected` / `handlePeerDisconnected` explicitly. There is no automatic wiring to `TransportListener` yet.
- Presence is in-memory only; no persistence across process restarts.
- `PeerPresenceManager` does not expose presence history; only the current snapshot is queryable.
