# Phase 3 Post-Implementation Report: S3.4 → S3.5

**Project:** Aryntra Pravah
**Version baseline:** `v0.3.3` (S3.1–S3.3 complete, peer identity/registry/routing operational)
**Report date:** 2026-09-18
**Author:** Implementation team
**Audience:** Senior Developer / Architecture Review

---

## Executive Summary

Phase 3 sprints S3.4 and S3.5 evolved Pravah from a system that could route messages to *logical peers* into a system that can **autonomously discover peers on the local network and maintain a meaningful, first-class model of their current availability**.

Before S3.4, the application layer could say:

```java
router.send(PeerId.of("peer-b"), message);
```

but only if some external actor had already registered `peer-b` in the `PeerRegistry` with an active connection ID. Discovery and presence were entirely manual concerns.

After S3.5, the system can say:

> "I have discovered a peer named `peer-b` on my local network at `192.168.1.42:6002`. It is currently `AVAILABLE`. When an active TCP connection is established, its presence will transition to `CONNECTED`. If the connection drops, it will fall back to `AVAILABLE` (if within the TTL window) or `UNAVAILABLE` (if beyond)."

**All 121 baseline tests remain green. Total test count is now 172/172 passing (+51 tests, +42.1%).**

**Zero source files from Phase 0, 1, 2, or S3.1–S3.3 were modified.** Both new subsystems were layered strictly on top of the existing architecture through well-defined new packages (`peer.discovery`, `peer.presence`).

---

## 1. Baseline & Constraints

At the start of S3.4, the system had:

- A complete framing layer (`FrameEncoder` / `FrameDecoder`) over length-prefixed TCP streams (16 MB max frame).
- A protocol layer (`MessageEncoder` / `MessageParser` / `ProtocolSessionManager`) with deterministic JOIN / MESSAGE / LEAVE semantics.
- A transport abstraction (`Transport`) with a TCP implementation (`TcpTransport`) supporting multiple concurrent connections identified by `socket.getRemoteSocketAddress().toString()`.
- A logical peer identity model (`PeerId`), an in-memory thread-safe `PeerRegistry` mapping `PeerId → PeerRecord(connectionId)`, and a `PeerRouter` translating `send(PeerId, Message)` into the encoder → framer → transport pipeline.
- **No mechanism** for a node to learn about other nodes without an out-of-band trigger.
- **No mechanism** for reasoning about whether a known peer is currently around, currently connected, or long gone.

**Hard constraints enforced throughout:**

1. `Transport.java`, `TransportListener.java`, `TcpTransport.java` must not be modified.
2. `Message.java` (immutable record), `MessageEncoder`, `MessageParser`, `FrameEncoder`, `FrameDecoder`, `ProtocolSessionManager`, and protocol `PeerState` are protected.
3. `PeerId`, `PeerRecord`, `PeerRegistry`, `PeerRouter`, `PeerRoutingException` from S3.1–S3.3 must not be mutated.
4. No authentication, encryption, persistence, multi-transport dispatch, offline queueing, or automatic retry was in scope.
5. Discovery must not silently redefine the routing semantics of `PeerRouter`.

All constraints were honored.

## 2. S3.4 — LAN Peer Discovery

### 2.1 Problem framing

Discovery answers exactly one question:

> **"Who is available around me?"**

It does not answer *how to route optimally*, and it does not replace the transport. The architectural separation kept during the sprint was:

```
Discovery  →  Peer identity + reachable endpoint
Registry   →  known peers
Routing    →  can I send right now?
Transport  →  bytes on the wire
```

Discovery is a network input boundary and is therefore treated as untrusted: LAN traffic can contain arbitrary bytes, and the discovery layer must never allow malformed traffic to crash the node or pollute the peer registry.

### 2.2 What was built

Four new classes in a new package `com.aryntra.pravah.peer.discovery`.

#### 2.2.1 `DiscoveryPacket` — the wire format

A deliberately separate wire format from the application `Message` format. Discovery and chat have different responsibilities and different lifecycles, and coupling them would have made both harder to evolve.

Layout:

```
+----------+---------+----------+--------------+----------+
| MAGIC(4) | VER(1)  | ID_LEN(2)| PEER_ID(N)   | PORT(2)  |
|  "PRAH"  |  0x01   |  ushort  |  UTF-8       |  ushort  |
+----------+---------+----------+--------------+----------+
```

- **Minimum packet size:** 10 bytes (4 + 1 + 2 + 1 + 2).
- **Magic bytes** (`PRAH`, ASCII) filter out random LAN UDP noise before any parsing.
- **Version byte** (`0x01`) reserves forward compatibility.
- **Length-prefixed UTF-8 peer ID** avoids delimiter escaping and supports multibyte identities.
- **TCP port** as unsigned short (1–65535).

Deserialization is strict. Invalid magic, unsupported version, zero-length peer ID, and truncated payloads all raise `IllegalArgumentException` and are silently dropped by the receiver (with `Invalid magic marker` specifically not logged, since it is expected LAN noise).

Notably, **the sender's IP address is not embedded in the packet payload**. It is derived from the incoming UDP datagram's source address. This makes IP spoofing at the discovery layer strictly a network-level concern, not a wire-format concern.

24 unit tests lock this behavior: round-trip, edge ports (1, 65535), UTF-8 multibyte (Devanagari + emoji), null / blank / oversized rejection, invalid magic rejection, unsupported version rejection, zero-length ID rejection, truncated payload rejection.

#### 2.2.2 `DiscoveredPeer` — the domain model

An immutable record:

```java
public record DiscoveredPeer(
    PeerId peerId,
    String hostAddress,
    int port
) { ... }
```

`DiscoveredPeer` reuses the existing `PeerId` class. No `LanPeerId` or `DiscoveryPeerId` variant was introduced. This was a deliberate architectural discipline: identity is orthogonal to how it was learned.

The separation `PeerId` = WHO, `hostAddress + port` = WHERE is preserved. `PeerId` never becomes an encoded IP.

13 unit tests: constructor validation, equality, null / blank host rejection, port boundary validation.

#### 2.2.3 `PeerDiscoveryListener` — the event contract

A minimal functional interface:

```java
@FunctionalInterface
public interface PeerDiscoveryListener {
    void onPeerDiscovered(DiscoveredPeer peer);
}
```

Kept intentionally single-method. Multiple listeners can subscribe. Presence and registry integration happen in a separate coordinator (see S3.5, section 3.5.5), not by overloading this interface.

#### 2.2.4 `LanPeerDiscovery` — the engine

A standard-library UDP broadcast implementation. No external dependencies were introduced.

**Concurrency model:**

- One **daemon receiver thread** blocking on `DatagramSocket.receive()`.
- One **single-threaded scheduled executor** for periodic broadcast announcements.
- Both threads are named (`pravah-discovery-rx-<peerId>`, `pravah-discovery-tx-<peerId>`) for diagnostic clarity.

**Socket configuration:**

The receiver socket is deliberately constructed unbound, configured with `SO_REUSEADDR`, then bound:

```java
rxSocket = new DatagramSocket(null);
rxSocket.setReuseAddress(true);
rxSocket.setBroadcast(true);
rxSocket.bind(new InetSocketAddress(discoveryPort));
```

This is essential to allow multiple Pravah instances on the same physical host to bind the same discovery UDP port, which is critical for local integration testing and for multi-instance deployments. Without pre-bind `SO_REUSEADDR`, the second node's `bind` call fails.

The transmitter socket is bound to an ephemeral port with broadcast enabled.

**Self-exclusion:**

A node ignores its own broadcasts by matching the parsed logical `PeerId` against `localPeerId`. This is done at the `PeerId` level, not at the IP level — a node hearing its own packet reflected back through the network stack will filter it correctly regardless of interface.

**Broadcast target:**

`255.255.255.255` was chosen over multicast. Rationale:

- Zero configuration; no group joining or TTL selection.
- Works uniformly across common LAN topologies.
- No dependency on IGMP behavior or router multicast support.

Multicast (`224.x.x.x` or `239.x.x.x`) remains a future option if bandwidth or LAN-hygiene concerns emerge.

**Lifecycle:**

- `start()` and `stop()` are guarded by a synchronization lock and are **idempotent**. Repeated `start()` warns and returns; repeated `stop()` is a silent no-op.
- Shutdown ordering is explicit and important:
  1. `broadcasterExecutor.shutdownNow()` + await.
  2. Close both sockets. Closing `rxSocket` immediately unblocks the receiver thread's `receive()` call.
  3. Interrupt the receiver thread and join with a 2-second timeout.
- Daemon threads ensure the JVM can exit even if `stop()` is skipped.

**Error handling:**

- `SocketException` inside the receiver loop is treated as expected during shutdown (when `!isRunning()`).
- Malformed packets with invalid magic are dropped silently.
- All other malformed packets are logged at `FINE` level.
- Listener callbacks are wrapped in try-catch to prevent a single misbehaving listener from killing the receiver thread.

**Testing:**

- Constructor validation (invalid PeerId, invalid ports, invalid TTL).
- Idempotent lifecycle (start → start → stop → stop, verifying state and no leaked threads).
- **Live UDP integration test:** two `LanPeerDiscovery` instances on the same host with different `PeerId`s and different TCP ports, discovering each other via real UDP broadcast on a test port. Verifies mutual discovery, correct advertised TCP port, and self-exclusion (Node A never discovers itself, Node B never discovers itself).

The integration test uses a 50ms broadcast interval and polls with a 3-second timeout ceiling, which has proven stable across multiple runs.

### 2.3 What was deliberately not built

- No authentication of discovered peer identities. Any node claiming `PeerId.of("alice")` is registered as `alice`. Consistent with the existing peer subsystem's stated non-goal.
- No automatic TCP connection establishment. Discovery registers the peer as `PeerRecord.disconnected(peerId)`; establishing the actual connection is a separate concern (see 3.5.5 for how S3.5 integrates with connection lifecycle).
- No multicast, no mDNS, no cross-subnet discovery.
- No rate limiting or backpressure on incoming discovery packets. In a hostile LAN, a peer could be flooded; this is deferred.

## 3. S3.5 — Peer Presence

### 3.1 Problem framing

Discovery alone does not tell you whether a peer is *currently* available. Consider:

```
10:00 → Peer B is discovered.
10:05 → Peer B silently disappears (crash, network loss, laptop lid closed).
10:20 → PeerRegistry still says "peer-b is known".
```

Without presence, the application has no honest way to answer "is peer-b around right now?"

Presence answers exactly:

> **"What is the current availability state of a known peer?"**

It does not answer whether the peer is cryptographically authentic, whether delivery is guaranteed, or whether the peer will still be around next second. Those are different problems.

Critically, presence was designed to be **explicitly distinct from protocol session semantics**. The protocol `PeerState` (`JOINED` / `LEFT`) describes chat session membership. A peer can be reachable on the network but not part of any active chat session, and vice versa. Overloading `PeerState` to carry availability would have entangled two orthogonal concerns.

### 3.2 State model

Four states form a small directed graph:

```
                    ┌────────────┐
                    │  UNKNOWN   │
                    └─────┬──────┘
                          │  reportDiscovered / reportConnected
                          ▼
              ┌─────────────────────────┐
              │       AVAILABLE          │◄──────┐
              └────┬──────────────┬─────┘       │
                   │              │             │
       reportConnected      TTL expiry          │ reportDisconnected
                   │              │             │ (within TTL)
                   ▼              ▼             │
            ┌───────────┐   ┌────────────┐      │
            │ CONNECTED │──►│ UNAVAILABLE│      │
            └─────┬─────┘   └────┬───────┘      │
                  │              │              │
                  │ reportDisconnected          │
                  │ (past TTL)                  │
                  └─────────────────────────────┘
```

- **UNKNOWN** — never observed.
- **AVAILABLE** — discovered on LAN with host/port metadata, but no active TCP connection.
- **CONNECTED** — an active connection reference exists.
- **UNAVAILABLE** — previously known, but gone silent (past TTL) or connection dropped past TTL.

Two design rules govern transitions:

1. **CONNECTED overrides discovery updates.** A discovery packet arriving while a peer is CONNECTED refreshes `lastSeen` and metadata but does not downgrade the state.
2. **TTL expiry only affects AVAILABLE.** A CONNECTED peer cannot be evicted by silence, because an active connection is stronger evidence of liveness than a discovery timestamp.

### 3.3 What was built

Five classes in a new package `com.aryntra.pravah.peer.presence`.

#### 3.3.1 `PeerPresenceState`

A four-value enum. Deliberately distinct from protocol `PeerState`. No overlap.

#### 3.3.2 `PeerPresence`

An immutable record:

```java
public record PeerPresence(
    PeerId peerId,
    PeerPresenceState state,
    String hostAddress,
    int port,
    Instant lastSeen
) { ... }
```

Provides `PeerPresence.unknown(peerId)` for queries against never-observed peers. This avoids returning `Optional` for the common "just show me the state" API and gives callers a sensible default instead.

#### 3.3.3 `PeerPresenceListener`

A minimal callback:

```java
@FunctionalInterface
public interface PeerPresenceListener {
    void onPresenceChanged(PeerId peerId, PeerPresence oldPresence, PeerPresence newPresence);
}
```

Fires only on **actual state transitions**. Same-state updates (e.g. a second discovery packet from an already-AVAILABLE peer) update `lastSeen` internally but do not invoke listeners. This dedup rule was tested explicitly.

#### 3.3.4 `PeerPresenceManager`

The coordinator.

**Concurrency model:**

- `ConcurrentHashMap<PeerId, PeerPresence>` for storage.
- All state transitions go through `map.compute(peerId, ...)` for atomic read-modify-write. No explicit locking on the map itself.
- Listeners are stored in `CopyOnWriteArrayList` to allow safe iteration during dispatch even if a listener registers or unregisters during a callback.
- Lifecycle transitions (`start` / `stop`) are guarded by a `stateLock` object.

**Input events:**

- `reportDiscovered(PeerId, host, port)` — sets AVAILABLE (or keeps CONNECTED if already connected), refreshes `lastSeen`, records host/port.
- `reportConnected(PeerId)` — sets CONNECTED, refreshes `lastSeen`, preserves any known host/port metadata.
- `reportDisconnected(PeerId)` — no-op if peer wasn't CONNECTED. Otherwise transitions to AVAILABLE (if `lastSeen` is within TTL) or UNAVAILABLE (if past). Note: preserves original `lastSeen` rather than resetting it, so the TTL check reflects the *last successful observation*, not the disconnect time.

**Expiry mechanism:**

- A `ScheduledExecutorService` runs `checkExpiry()` at interval `max(100ms, TTL/2)`.
- `checkExpiry()` iterates the map and, using `computeIfPresent`, transitions AVAILABLE peers whose `lastSeen` is older than the threshold to UNAVAILABLE.
- CONNECTED peers are never touched by this loop.
- The scheduler thread is a named daemon (`pravah-presence-expiry`).

**Lifecycle:**

Same idempotency guarantees as `LanPeerDiscovery`. Repeated `start()`/`stop()` are safe. Shutdown uses `shutdownNow()` + 2-second await.

**Testing:**

- Constructor validation (positive TTL required).
- Lifecycle idempotency.
- UNKNOWN → AVAILABLE on discovery.
- UNKNOWN → CONNECTED on connection.
- CONNECTED → AVAILABLE on disconnect within TTL.
- Listener deduplication (same-state updates do not fire).
- **Live background expiry test:** a real 150ms TTL manager with two peers — one silent AVAILABLE and one CONNECTED. Uses a `CountDownLatch` to wait for the silent peer's actual transition to UNAVAILABLE, then asserts the CONNECTED peer was preserved. This test verifies the scheduled expiry thread actually fires and takes the correct action.

#### 3.3.5 `PeerPresenceBridge` — the integration coordinator

This was the architectural piece that tied it all together without modifying any protected code.

`PeerPresenceBridge` implements `PeerDiscoveryListener` and holds references to a `PeerRegistry` and a `PeerPresenceManager`. It is the single choke point where discovery, registry, and presence meet.

Three responsibilities:

**1. On discovery** (via the implemented listener interface):

```java
public void onPeerDiscovered(DiscoveredPeer peer) {
    presenceManager.reportDiscovered(peer.peerId(), peer.hostAddress(), peer.port());
    if (!registry.contains(peer.peerId())) {
        registry.register(PeerRecord.disconnected(peer.peerId()));
    }
}
```

Discovery updates presence unconditionally. Registration is idempotent — only newly-discovered peers are added as `disconnected` records, so an already-registered CONNECTED peer is not accidentally downgraded in the registry.

**2. On connection** (application/session manager calls this explicitly):

```java
public void handlePeerConnected(PeerId peerId, String connectionId) {
    registry.register(peerId, connectionId);
    presenceManager.reportConnected(peerId);
}
```

Registry gets the active connection ID; presence transitions to CONNECTED. Both are ordered: registry first (so any concurrent routing attempt sees the connection), then presence.

**3. On disconnection**:

```java
public void handlePeerDisconnected(PeerId peerId) {
    registry.register(PeerRecord.disconnected(peerId));
    presenceManager.reportDisconnected(peerId);
}
```

Registry connection ID is nulled; presence transitions per its rules.

**Explicit non-goal:** the bridge does not automatically wire itself into `TransportListener` or `ProtocolSessionManager`. Those wirings would require touching protected code and were deferred to S3.6. Right now, the application or a higher-level coordinator must invoke `handlePeerConnected` / `handlePeerDisconnected` when it observes transport events.

**Testing:**

Three integration tests:

- Discovery flow: `onPeerDiscovered(peer)` results in a registered-but-disconnected peer in the registry AND presence = AVAILABLE with correct host/port.
- Connection flow: `handlePeerConnected(peerId, "conn-999")` results in registry with `connectionId = "conn-999"` AND presence = CONNECTED.
- Disconnection flow: full discover → connect → disconnect cycle, verifying registry connectionId returns to `null`, presence returns to AVAILABLE (within TTL), and host/port metadata is preserved.

### 3.4 What was deliberately not built

- No heartbeat protocol. Presence is passive: it observes discovery packets and explicit connect/disconnect signals. Active liveness probing is not in scope.
- No offline queueing, no retry, no store-and-forward. Presence *informs* the application; it does not act on the application's behalf. `PeerRouter` semantics remain unchanged: sending to a disconnected peer still raises `PeerRoutingException` immediately.
- No multi-transport presence aggregation. A future world where a peer is AVAILABLE via LAN but UNAVAILABLE via Internet is not modeled; presence today is a single flat value per peer.
- No presence history. Only the current snapshot is queryable.
- No persistence. Everything is in-memory and lost on restart.
- No automatic wiring to `TransportListener`. The bridge exposes explicit `handlePeerConnected` / `handlePeerDisconnected` methods that must be invoked by the caller. Automatic wiring is deferred to S3.6.

## 6. Architectural decisions and their justifications

### 6.1 Separate wire format for discovery

Reusing the `Message` format for discovery would have been superficially convenient — the encoder/parser already exist — but would have been architecturally corrosive. Discovery packets and application messages are:

- Sent over different transports (UDP vs TCP).
- Subject to different validation strictness (discovery must silently reject noise; messages must strictly reject any invalid input).
- Versioned on different timelines.
- Sized very differently (discovery is small; messages can be up to 16 MB).

Coupling them would have meant that any future evolution of the chat message format would require reasoning about backward compatibility with LAN discovery, and vice versa. The 40 lines of extra code in `DiscoveryPacket` are worth the clean separation.

### 6.2 UDP broadcast over multicast

`255.255.255.255` was chosen because it works out of the box in every LAN topology we care about, requires no group-join semantics, and has no dependence on router or switch IGMP behavior. Multicast is a legitimate future upgrade if we need bandwidth savings on very dense LANs, but that's a scaling concern, not an S3.4 concern.

### 6.3 Endpoint IP derived from datagram source, not embedded in payload

The discovery packet carries WHO (`PeerId`) and WHERE-port (`TCP port`) but not WHERE-IP. The receiver derives IP from the UDP datagram's source address. Rationale:

- The packet cannot lie about its source IP without cooperation from the network stack (spoofing is a network-level concern).
- It naturally handles NAT and multi-homed hosts: the packet advertises the port, but the IP is whatever route it took.
- It keeps the packet minimal.

### 6.4 Presence is not protocol session state

The temptation to overload `PeerState` (`JOINED` / `LEFT`) was real. Both describe a peer's status, both are updated by observed events. But they answer different questions:

- Protocol `PeerState`: "Is this peer participating in the current chat session?"
- `PeerPresenceState`: "Is this peer reachable on the network?"

A peer can be `AVAILABLE` (reachable via LAN) but `LEFT` (not in the chat session). A peer can be `CONNECTED` (active TCP link) but `LEFT` (silently sitting there without joining any session). Coupling these would have made both harder to reason about.

Two enums, two managers, two lifecycles. Cleanly separated.

### 6.5 Bridge as coordinator, not rewriter

`PeerPresenceBridge` was carefully scoped to *invoke* the registry and presence manager's public APIs, never to reach inside their state. This means:

- The bridge has no privileged access.
- The bridge can be replaced or subclassed without touching the registry or presence code.
- The bridge is fully testable with real (not mocked) `PeerRegistry` and `PeerPresenceManager` instances, which is how the tests are actually written.

This also means the bridge is *optional*. An application that wants only discovery (no presence) or only presence (no discovery) can use the underlying classes directly.

### 6.6 Explicit connection/disconnection hooks, not automatic wiring

`PeerPresenceBridge.handlePeerConnected(peerId, connectionId)` and `handlePeerDisconnected(peerId)` are called explicitly by the application. They are not automatically triggered by `TransportListener` or `ProtocolSessionManager` callbacks.

This was intentional. Automatic wiring would have required:

- Modifying `TransportListener` to add lifecycle callbacks (currently it only has `onDataReceived`), which is a protected contract change.
- OR wrapping `TcpTransport` in a subclass or decorator, which introduces its own lifecycle complexity.
- OR intercepting `ProtocolSessionManager` events, which conflates transport-level presence with protocol-level session membership.

All three options were deferred to S3.6, where the wiring can be designed with full awareness of the tradeoffs. For S3.5, explicit invocation is honest, testable, and non-invasive.

### 6.7 TTL expiry preserves original `lastSeen` on disconnect

When a CONNECTED peer disconnects, `reportDisconnected` transitions the presence state but does *not* update `lastSeen`. This means the TTL check reflects the last observed discovery, not the disconnect moment.

Rationale: `lastSeen` semantically means "most recent evidence the peer is alive on the network." A disconnect event is evidence of the *opposite* — the peer is less alive now. Updating `lastSeen` at disconnect would give a disconnected peer an artificial life extension.

The practical effect: if a peer was last discovered 10 minutes ago and its TCP connection just dropped, and the TTL is 30 seconds, the peer immediately becomes UNAVAILABLE — which is correct. If it was last discovered 2 seconds ago and the connection dropped, it becomes AVAILABLE — which is also correct, because we have strong recent evidence it exists.

### 6.8 Presence expiry granularity capped at 100ms

`checkExpiry` runs at `max(100ms, TTL/2)`. Below 100ms, scheduler jitter, GC pauses, and OS thread scheduling dominate any perceived "precision." Callers requesting a 10ms TTL would get 100ms resolution, which is honest.

### 6.9 Idempotent lifecycle everywhere

Both `LanPeerDiscovery` and `PeerPresenceManager` support repeated `start()`/`stop()` without side effects. This mirrors the discipline of the existing `TcpTransport` and makes both classes safe to embed in higher-level orchestration that may not track lifecycle precisely.

## 7. Known limitations and future work

### 7.1 Discovery

- **Subnet-bounded.** UDP broadcast does not cross routers. Cross-subnet discovery requires either a rendezvous server, multicast (with router support), or an application-level relay.
- **No rate limiting.** A hostile or misbehaving LAN peer could flood our discovery listener. The receiver thread would keep up (there's no processing backpressure), but the presence manager could see thrashing updates.
- **No packet authentication.** Any node can claim any `PeerId`. This is a Phase 4+ concern.
- **`SO_REUSEADDR` semantics vary across OSes.** On Linux, `SO_REUSEADDR` behaves as needed. On Windows and macOS, behavior is close but not identical, and multi-host testing may reveal subtle differences.
- **No IPv6 broadcast.** IPv4 broadcast only; IPv6 requires multicast.

### 7.2 Presence

- **No heartbeat.** Silent peers only expire via the TTL mechanism after their last discovery observation. If discovery packets are lost (busy LAN, WiFi contention), a peer may transition to UNAVAILABLE despite being genuinely alive.
- **No presence history.** Only current state is queryable.
- **No persistence.** All state is lost on process restart.
- **Bridge is not automatically wired.** Application code must explicitly call `handlePeerConnected` / `handlePeerDisconnected`. Deferred to S3.6.
- **No multi-source aggregation.** A future world with multiple transports (Bluetooth, Internet) would need presence to reason about per-transport availability, which the current flat state cannot express.

### 7.3 Integration

- The bridge assumes a 1:1 mapping between a `PeerId` and a `connectionId`. Multi-connection scenarios (a peer reachable via two simultaneous TCP links) would require extending `PeerRecord`, which was called out in the S3.1–S3.3 report as a known future pressure point.

## 8. Suggested next steps (S3.6 and beyond)

### 8.1 S3.6 — End-to-End Peer Integration

The natural next sprint. Concretely:

- Extend `TransportListener` (protected!) with connection lifecycle callbacks: `onConnectionOpened(connectionId, remoteAddress)` and `onConnectionClosed(connectionId)`. This is the first justified protected-contract change and should be an ADR.
- Wire `TcpTransport` to invoke these callbacks.
- Introduce a `PeerConnectionCoordinator` that observes transport lifecycle, maps `connectionId ↔ PeerId` (probably via observed JOIN messages, since a fresh connection doesn't yet have a peer identity), and invokes `PeerPresenceBridge.handlePeerConnected` / `handlePeerDisconnected` automatically.
- Demonstrate a full pipeline: two nodes on LAN → mutual discovery → automatic TCP connection → JOIN handshake → presence CONNECTED → LEAVE → presence AVAILABLE → silence → presence UNAVAILABLE.

### 8.2 ADR candidates

Two architectural decisions from S3.4–S3.5 warrant formal ADRs if not already documented:

- **ADR-004: Discovery wire format separation from application Message format.** Rationale, alternatives considered, migration implications.
- **ADR-005: Peer presence as a distinct concept from protocol session state.** Rationale, alternatives (overloading `PeerState`), and the framework for future multi-transport presence.

### 8.3 Longer horizon

- Multi-connection `PeerRecord`: extend to `List<connectionId>` or `Map<TransportType, connectionId>`.
- Heartbeat protocol layered above `PeerRouter` for active presence probing.
- Persistence layer for peer identity and known-peer history.
- Rate limiting on discovery input.
- Cryptographic peer identity (public-key based `PeerId`).
