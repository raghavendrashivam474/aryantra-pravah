## 3. Issue #1 — `CONNECT ERROR: null`

### 3.1 Evidence

```
[21:19:09] DISCOVERED: android-2043f28c @ 10.177.67.157:39407
[21:19:15] Connecting to android-2043f28c @ 10.177.67.157:39407...
[21:19:15] CONNECT ERROR: null
```

### 3.2 Root Causes (two, both present simultaneously)

**Cause A — `NetworkOnMainThreadException`:**
Android strictly forbids socket operations (`Socket.connect`) on the UI thread. This exception's detail message is `null`, and the UI logged `e.message` directly — producing the useless `CONNECT ERROR: null`.

**Cause B — Loopback-only server binding:**
`PravahAndroidMessagingManager` defaulted `host = "127.0.0.1"`. The `ServerSocket` therefore only listened on loopback and physically could not accept an inbound connection from `10.177.67.x` even if Cause A was fixed.

### 3.3 Fixes

| Fix | File | Detail |
|---|---|---|
| Wildcard binding | `PravahAndroidMessagingManager.kt` | Default `host` changed `127.0.0.1` → `0.0.0.0` |
| Off-main-thread execution | `DiagnosticActivity.kt` | All network operations (`start`, `stop`, `connectTo`, `sendJoin`, `replyJoin`, `sendText`) dispatched via single-thread `backgroundExecutor`; results posted back via `Handler(Looper.getMainLooper())` |
| Honest error logging | `DiagnosticActivity.kt` | `val err = e.message ?: e.javaClass.simpleName` — a null-message exception now logs its class name |

### 3.4 Lessons

1. **Never log `e.message` alone on Android.** Several Android framework exceptions (notably `NetworkOnMainThreadException`) have `null` messages. Always log `e.javaClass.simpleName` as a fallback.
2. **`127.0.0.1` is correct for JVM unit tests, wrong for physical device roles.** Any peer that must accept LAN connections must bind `0.0.0.0`. This distinction did not exist in S7.1–S7.4 because tests were all loopback.
3. Android's main-thread network prohibition never surfaced in automated JVM tests — it is a runtime-platform behavior. **Physical device testing exists to catch exactly this class of defect.**

## 4. Issue #2 — One-Way Messaging (Phone → Tablet works; Tablet → Phone silently lost)

### 4.1 Evidence (the defining symptom)

Phone (`android-90931ae4`):
```
[21:24:34] JOIN sent to android-0bd61ef0
[21:24:35] Session state: null          ← the honest clue
[21:24:42] > SENT: hello
[21:24:43] Delivery pending/completed.  ← no ACK ever arrives
```

Tablet (`android-0bd61ef0`):
```
[21:24:43] < RECV [android-90931ae4]: hello     ← inbound works
[21:24:33] > SENT: yep!
[21:24:36] Dispatched to router.                ← reply dispatched, never arrives
```

Phone's status bar also literally displayed `Session: android-0bd61ef0 [null]` in the first test — the state machine was telling us the answer from the start.

### 4.2 Investigation Trail (including the false leads — preserved deliberately)

**Hypothesis A — "Receiver UI never binds the session":** Partially true but not causal. The Tablet's input/SEND stayed disabled because `connectedPeerId` was only set on the initiator. Fixing this (auto-bind on inbound `ApplicationMessage`) was *necessary for the Tablet to be able to reply at all*, but replies still vanished. UI-layer fix, not root cause.

**Hypothesis B — "PeerRouter can't resolve the inbound connection":** Investigated deeply. `TcpTransport.attachActiveSocket` names connections by `socket.getRemoteSocketAddress().toString()`; the coordinator registers exactly that ID on inbound JOIN via `presenceBridge.handlePeerConnected(peerId, connectionId)`, so registry ↔ transport keys matched on both sides. Hardening applied (3-arg `PeerRouter` constructor with `connectivityRegistry`; explicit `handlePeerConnected` in `sendJoin`) — *defensive, not causal*. Routing was never the failure point.

**Regression incident (caught by tests, exactly as the sprint brief demanded):**
The first attempt at auto-replying JOINs installed a `ProtocolListener` directly via `coordinator.setProtocolListener(...)`. This **overwrote** the listener that `DefaultApplicationMessagingService` installs on the coordinator — the component that handles inbound chat → auto-ACK and inbound ACK → outbox `COMPLETED`. Result: 4 unit tests failed instantly (Scenarios 4, 5&6, 7, 10 — all message-delivery paths). No test was edited; the approach was reverted and replaced with listener *chaining*. **The S7.4 test suite acted as the architectural safety net it was designed to be.**

**Diagnostic-UI anti-pattern discovered during investigation:**
A later UI revision changed the status display to `state ?: PeerState.JOINED` — defaulting an unknown session state to JOINED. This **masked the real `null` state** that had been visible in the first test and delayed diagnosis. Rule recorded: *a diagnostic tool must display raw state; it must never default unknown → expected.*

### 4.3 Definitive Root Cause

**The JOIN handshake was one-directional, and the protocol session state is intentionally asymmetric.**

Frame-by-frame trace:

1. Phone → Tablet: `JOIN (sender=Phone)` — Tablet's `ProtocolSessionManager` sets **Phone = JOINED**. ✅
2. Phone calls `replyJoin(Tablet)` — but this method (misnamed) sends **another JOIN with `sender=Phone`** to Tablet. It does not, and cannot, produce a JOIN from Tablet. Tablet is already JOINED for Phone; duplicate JOIN is rejected (`ProtocolException`, caught and logged fine).
3. **No frame with `sender=Tablet, type=JOIN` ever reached Phone.** Phone's `ProtocolSessionManager` therefore held **Tablet = null**.
4. Every subsequent Tablet → Phone frame (`MESSAGE` chat payloads and the automatic `APP_MSG_ACK`) hit Phone's session manager, which enforced the protocol contract:

   > `ProtocolException: Peer 'android-XXXX' cannot send MESSAGE before JOIN`

5. Phone's engine discarded those frames at the **protocol session layer** — after successful TCP delivery, after successful frame decode, after successful parse. That is why the symptom looked like "dispatched to router and vanished": transport and routing were healthy the whole time.

This was never an Android bug, a threading bug, a routing bug, or a reliability bug. It was a **handshake composition bug in the S7.5 diagnostic layer**: the existing core requires each peer's state machine to *observe* the other peer's JOIN, and nothing in the composition guaranteed that.

### 4.4 The Fix — Transparent ProtocolListener Chaining

`PravahAndroidMessagingManager` now constructs an anonymous subclass of `PeerConnectionCoordinator` that overrides `setProtocolListener` to **wrap instead of replace**:

```kotlin
val coordinator = object : PeerConnectionCoordinator(transport, registry, presenceBridge) {
    private var downstreamListener: ProtocolListener? = null

    override fun setProtocolListener(listener: ProtocolListener?) {
        this.downstreamListener = listener
        super.setProtocolListener(object : ProtocolListener {
            override fun onPeerJoined(peerIdStr: String, message: Message) {
                // 1. Forward untouched to DefaultApplicationMessagingService
                downstreamListener?.onPeerJoined(peerIdStr, message)
                // 2. Reciprocal JOIN on initial inbound JOIN
                if (message != null && message.messageId().startsWith("join-")) {
                    replyJoin(PeerId.of(peerIdStr))
                }
            }
            override fun onMessageReceived(p: String, m: Message) { downstreamListener?.onMessageReceived(p, m) }
            override fun onPeerLeft(p: String, m: Message)       { downstreamListener?.onPeerLeft(p, m) }
        })
    }
}
```

Properties of this fix:
- `DefaultApplicationMessagingService` remains the **sole owner** of session-event consumption — all events are forwarded untouched, which is why all 342 tests stayed green.
- The reciprocal JOIN fires exactly once per initial handshake (trigger keyed on the `join-` messageId prefix; the `reply-join-` reply does not re-trigger).
- The behavior lives in the **composition layer only**. Zero core Java changes. No ADR required.

### 4.5 Causal vs Defensive Changes (honest accounting)

| Change | File | Classification |
|---|---|---|
| `host = 0.0.0.0` | Manager | **Causal** (Issue #1) |
| Background executor for all network ops | Activity | **Causal** (Issue #1) |
| Exception class-name fallback logging | Activity | Diagnostic quality |
| `connectivityRegistry` passed to 3-arg `PeerRouter` | Manager | Defensive hardening |
| `presenceBridge.handlePeerConnected` in `sendJoin` | Manager | Defensive hardening (path-state consistency) |
| `bindSession` on inbound message (receiver UI unlock) | Activity | Enabling (required for receiver to reply at all) |
| **Transparent listener chaining + reciprocal `replyJoin`** | Manager | **Causal** (Issue #2 — the actual fix) |

## 5. Architectural Learnings (carry into Phase 8)

1. **JOIN is not implicitly symmetric.** The protocol contract requires each peer's `ProtocolSessionManager` to observe the other peer's JOIN. Any future connection initiation path (desktop, Android, Phase 8 transports) must guarantee a reciprocal JOIN, or one side will silently reject all frames with `cannot send MESSAGE before JOIN`.
2. **The coordinator's `ProtocolListener` is owned by `DefaultApplicationMessagingService`.** Extensions must wrap/chain, never replace. If multi-consumer listeners become a real Phase 8 requirement, the correct evolution is an `addProtocolListener` API on the coordinator — which is a **core API change requiring an ADR**, not a wrapper workaround.
3. **Transport and routing were never the problem.** Debugging layered systems requires resisting the urge to fix the layer you can see (UI, routing) before proving the layer where the symptom actually originates (protocol session state). The discarded "fixes" for routing remain as harmless hardening.
4. **Loopback vs wildcard binding is a deployment property, not a code property.** Phase 8 should make bind address an explicit, documented configuration decision per environment.
5. **A diagnostic UI must render raw state.** Defaulting `null → JOINED` in the display actively hid the root cause for one full debug cycle.
6. **Android platform behaviors (main-thread networking, multicast permissions, null-message exceptions) are invisible to JVM unit tests.** This is precisely the gap physical validation exists to close — and it worked.
