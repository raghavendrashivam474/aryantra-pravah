### 3.2 Critical Discovery — ACK Is Not a Wire Type

A key architectural insight that shaped S7.4:

- `MessageType` enum contains only `JOIN`, `MESSAGE`, `LEAVE` on the wire.
- **ACK is implemented at the application layer** inside `DefaultApplicationMessagingService` as a `MESSAGE` with a 1-byte app-type prefix:
  - `APP_MSG_CHAT       = 0x01` (direct chat)
  - `APP_MSG_ACK        = 0x02` (acknowledgment)
  - `APP_MSG_GROUP_CHAT = 0x03` (group chat)
- When `DefaultApplicationMessagingService` receives an `APP_MSG_CHAT`, it automatically dispatches an `APP_MSG_ACK` back to the sender via `sendApplicationAck()`.
- When it receives an `APP_MSG_ACK`, it calls `outbox.markCompleted(messageId)` and updates `MessageState` to `DELIVERED`.

This meant S7.4 did **not** need to implement any ACK logic — it only needed to wire the service correctly so the automatic ACK roundtrip would occur.

### 3.3 Final Message Path (Reused End-to-End)

```
ApplicationMessage (sender)
   ↓
DefaultApplicationMessagingService.sendText()
   ↓  (frames as APP_MSG_CHAT)
PeerRouter.send(PeerId, Message)
   ↓  (resolves PeerConnectivityRegistry → active ConnectionId)
MessageEncoder → FrameEncoder
   ↓
TcpTransport.send(connectionId, bytes)
   ↓
──────── TCP ────────
   ↓
TcpTransport.onDataReceived
   ↓
PeerConnectionCoordinator (FrameDecoder → MessageParser)
   ↓
ProtocolSessionManager.processMessage
   ↓
DefaultApplicationMessagingService.handleInboundProtocolMessage
   ↓
  switch (appType):
    APP_MSG_CHAT → listener.onMessage(appMessage) + auto-send APP_MSG_ACK
    APP_MSG_ACK  → outbox.markCompleted + MessageState.DELIVERED
```

### 4.3 `PravahAndroidMessagingManager` Design

The manager is a Kotlin composition class — not a wrapper, not a translation layer. It constructs the standard Pravah object graph in the correct order:

```kotlin
val transport        = TcpTransport(host, port)
val registry         = PeerRegistry()
val presenceManager  = PeerPresenceManager(2000L)
val presenceBridge   = PeerPresenceBridge(registry, presenceManager)
val coordinator      = PeerConnectionCoordinator(transport, registry, presenceBridge)
val router           = PeerRouter(registry, transport)
val historyStore     = InMemoryMessageHistoryStore()
val outbox           = InMemoryDeliveryOutbox()
val messaging        = DefaultApplicationMessagingService(
    localPeerId, router, coordinator, historyStore, outbox
)
```

Public API exposed:
- `start()`, `stop()`, `close()` — lifecycle
- `connectTo(host, port)` — physical TCP
- `sendJoin(peerId, connId)`, `replyJoin(peerId)` — protocol handshake
- `sendText(peerId, content)` — application messaging
- `addMessageListener(listener)` — inbound events

The manager does not expose `Socket`, `Transport`, framing primitives, or any Android-specific types above the `PeerId` boundary.

### 4.4 Persistence Decision — In-Memory Only

Per Brief §41 (Risk 2), SQLite-JDBC was flagged as a potential Android risk. **I did not preemptively replace it**. Instead:
- The manager uses `InMemoryMessageHistoryStore` and `InMemoryDeliveryOutbox` as safe defaults.
- The SQLite implementations remain available for the JVM runtime.
- The decision whether to adopt Android's native SQLite is **deferred** to Phase 8, where it can be driven by real device evidence rather than speculation.

This is a composition-time choice, not an architectural change — no ADR needed.

## 6. Problems Encountered and Mitigations

This section documents every notable problem encountered during implementation, in the order they occurred.

### 6.1 Environment: PowerShell Compatibility
- **Problem:** The host system uses Windows PowerShell 5.1, which does not support `Get-ChildItem -MaxDepth`, Bash-style `-or` conditionals, or Unix-style `./gradlew` (missing `.bat` extension).
- **Impact:** First attempts to run `./gradlew test` and recursive file listings failed.
- **Mitigation:** Switched to `.\gradlew.bat`, replaced `-MaxDepth` with `-Recurse` + filtering, and rewrote conditional logic using separate `if`/`elseif` with proper PS 5.x syntax. No code changes required.

### 6.2 Build System: Dual-Root Discovery
- **Problem:** The repository uses **Maven** for the core (`pom.xml` at root) and **Gradle** for the Android subproject (`android/build.gradle.kts`). This was not immediately obvious.
- **Impact:** Running `mvn test` at root covers 319 tests; running `gradlew test` from `android/` covers Android tests. Neither alone provides the full baseline.
- **Mitigation:** Executed both suites. Documented the dual-root layout in the sprint report. Final verification requires running both: `mvn test && (cd android; .\gradlew.bat test)`.

### 6.3 Protocol Architecture: ACK Is Not a Wire Type
- **Problem:** My initial assumption (based on the Brief's conceptual diagrams) was that `MessageType` would include an `ACK` value. It does not — the enum is strictly `{JOIN, MESSAGE, LEAVE}`.
- **Impact:** If I had built an `AndroidAckManager` as the Brief warned against, I would have duplicated existing functionality.
- **Mitigation:** Deeper inspection of `DefaultApplicationMessagingService` revealed that ACK is implemented at the application layer as `APP_MSG_ACK (0x02)` payload prefix inside a `MESSAGE`. The entire ACK roundtrip is handled automatically — I only needed to wire the service correctly. **No ACK code was written on the Android side.**

### 6.4 Persistence: SQLite-JDBC on Android (Deferred Risk)
- **Problem:** The core reliability stack uses `sqlite-jdbc`, which bundles a native binary (`libsqlitejdbc.so`) built for desktop JVMs. This native library is not compatible with Android's Dalvik/ART runtime and would fail at load time if invoked on-device.
- **Impact:** Any Android code path that touches `SqliteMessageHistoryStore` or `SqliteDeliveryOutbox` would crash with `UnsatisfiedLinkError`.
- **Mitigation:** Followed Brief §41 (Risk 2) guidance — did **not** preemptively replace the architecture. Instead, selected `InMemoryMessageHistoryStore` and `InMemoryDeliveryOutbox` as the composition-time defaults in `PravahAndroidMessagingManager`. This is a configuration decision, not an architectural one. The SQLite implementations remain the authoritative durable persistence for JVM. A proper Android persistence strategy (likely Android Room or `android.database.sqlite`) should be decided in Phase 8 based on real durability requirements, not speculation.

### 6.5 Session Handshake: Mismatched JOIN Pattern
- **Problem:** The Phase 4 end-to-end test (`Phase4EndToEndApplicationIntegrationTest`) uses a **manual** JOIN pattern where the first JOIN is dispatched via `transport.send(connectionId, framedBytes)` and only the reply JOIN uses `router.send()`. This asymmetry exists because the local router cannot resolve the remote peer until `PeerRegistry.register()` is called first.
- **Impact:** A naive attempt to use `router.send()` for the initial JOIN would fail with "no connection for peer" because the router has no mapping yet.
- **Mitigation:** Replicated the exact asymmetric pattern in `sendJoin()` (manual transport send after `registry.register()`) and `replyJoin()` (router-based). This mirrors the proven Phase 4 integration pattern and avoids introducing new handshake logic.

### 6.6 Known Limitation Carried Forward: `connectPath` Best-Effort Matching
- **Problem:** The S7.2 `PravahAndroidNetworkManager.connectPath()` method matches a `ConnectivityPath` to a `connectionId` by substring-matching the port number, with a first-active fallback. This is flagged in Brief §15 as acceptable for single-connection scenarios but potentially ambiguous under concurrent connections.
- **Impact under S7.4:** The S7.4 test scenarios use **one connection per peer pair**, so the ambiguity does not manifest. No test exposed incorrect path promotion.
- **Mitigation:** Per Brief §15 — did **not** redesign speculatively. The limitation is explicitly carried forward and documented. If Phase 8 introduces multiple concurrent paths per peer (e.g., hybrid transports), this will require revisiting with an ADR. For now, the behavior is correct for the current use case.

### 6.7 Test Reports: Non-Standard Output Path
- **Problem:** Standard Gradle test reports live in `build/reports/tests/test/`, but Android Gradle Plugin places them in `build/reports/tests/testDebugUnitTest/` and `testReleaseUnitTest/`. XML results live in `build/test-results/testDebugUnitTest/`.
- **Impact:** Initial automated report-parsing script failed with "path not found".
- **Mitigation:** Enumerated the Android build directory structure to locate the correct paths, then parsed XML results directly. Both debug and release variants are run — the same 23 tests appear in both suites, which is standard Android behavior and explains the "46 variant executions" figure.

### 6.8 Discovery: Debug/Release Duplicate Reporting
- **Problem:** When reading JUnit XML output, each test appears **twice** — once for the `testDebugUnitTest` task and once for `testReleaseUnitTest`.
- **Impact:** Raw totals showed 46 Android tests, which initially looked like a doubled count.
- **Mitigation:** Confirmed that Android Gradle Plugin runs unit tests for both build variants by default. The unique test count is 23 (14 pre-existing + 9 new S7.4), with 46 total executions. Both numbers are reported in the sprint documentation.

## 12. Recommendation for Phase 8

Per Brief §51, Phase 8 begins only after real-device evidence confirms the current architecture. Based on the implementation experience, I recommend Phase 8 scoping discussions include:

1. **Persistence on Android** — evidence-driven decision between keeping in-memory, adopting Android Room, or wrapping `android.database.sqlite` behind the existing `MessageHistoryStore` / `DeliveryOutbox` interfaces.

4. **Discovery hardening** — only if physical testing exposes IPv4 broadcast failures on real networks.

None of these should be undertaken speculatively.
