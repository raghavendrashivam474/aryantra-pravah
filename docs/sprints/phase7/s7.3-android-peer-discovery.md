# S7.3 — Android Peer Discovery

## Baseline
- Baseline: S7.2 complete
- Core Tests: 319 / 319 passing

## Objective
Bring the existing LAN discovery system onto Android without altering wire formats, preserving the strict decoupling of logical `PeerId` from transport endpoints, and ensuring idempotent candidate path mapping.

## Key Decisions & Implementation Details
1. **Reuse Existing Discovery Protocol**: Reused `LanPeerDiscovery`, `DiscoveryPacket`, and `DiscoveredPeer` directly.
2. **PravahAndroidDiscoveryManager**: Android discovery coordinator orchestrating UDP broadcast announcements, listener dispatch, and `PeerPresenceBridge`.
3. **Discovery ≠ Connection Invariant**:
   - Discovered peer events create a `PathState.CANDIDATE` path in `PeerConnectivityRegistry`.
   - Paths are only promoted to `PathState.ACTIVE` upon explicit connection establishment.
4. **Identity Decoupling**: Discovered Android devices maintain a stable, logical `PeerId` completely decoupled from IP addresses or socket descriptors.
5. **Duplicate Idempotency**: Repeated LAN announcements produce identical deterministic `PathId` entries, preventing duplicate path accumulation.
6. **Presence Lifecycle**: Fully aligned with `PeerPresenceManager` (TTL-based expiration from `AVAILABLE` to `UNAVAILABLE`).

## Verification Scenarios Tested
- **Scenario 1 (Discovery)**: Device A broadcasts UDP discovery packets; Device B receives and parses `DiscoveredPeer`.
- **Scenario 2 (Duplicate Idempotence)**: Repeated announcements for the same peer produce a single candidate path.
- **Scenario 3 (Candidate Path)**: Discovery registers a `PathState.CANDIDATE` path.
- **Scenario 4 (Connection Promotion)**: Connection establishment promotes candidate path to `PathState.ACTIVE`.
- **Scenario 5 (Disconnect Transition)**: Disconnect transitions active path to `PathState.INACTIVE` while preserving `PeerId`.
- **Scenario 6 (Presence Transitions)**: Validates complete lifecycle (`AVAILABLE` -> `CONNECTED` -> `AVAILABLE` -> `UNAVAILABLE` upon TTL expiry).
