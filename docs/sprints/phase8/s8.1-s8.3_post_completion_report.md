## 2. Sprint S8.1 — Hybrid Connectivity Contract

### 2.1 Objective
Define what "Hybrid Transport & Connectivity" means for Pravaah before writing any implementation code. Select Transport-B through evidence-based evaluation rather than assumption.

### 2.2 What Was Implemented

**ADR-013: Transport-B Selection — Bluetooth RFCOMM**
(`docs/architecture/ADR-013-transport-b-bluetooth-rfcomm.md`)

Evaluated four candidates against ten criteria:

| Candidate | Verdict | Key Reason |
|---|---|---|
| BLE (GATT) | Rejected | GATT request/response model doesn't map to streaming `Transport` contract; excessive implementation scope |
| Bluetooth RFCOMM | **Selected** | Stream-oriented sockets, native Android SDK, no cloud infra, genuinely heterogeneous from TCP/IP |
| QUIC | Rejected | Still IP-based (not meaningfully heterogeneous); requires third-party library |
| WebRTC | Rejected | Requires STUN/TURN/signaling infrastructure; violates S8.3 no-internet-infrastructure constraint |

**S8.1 Contract Document**
(`docs/sprints/phase8/s8.1-hybrid-connectivity-contract.md`)

Defined:
- Transport contract gap analysis (3 gaps identified, all resolvable without modifying existing interfaces)
- `TransportCapabilities` specification for Bluetooth RFCOMM
- Candidate → Path lifecycle rules
- Multi-path identity protection rules
- Compatibility assessment confirming zero modifications to existing core components

### 2.3 Key Architectural Decision

The existing `PeerRouter` holds a single `Transport transport` field. This is a known gap for multi-transport routing. The decision was made to **not** modify `PeerRouter` in S8.1–S8.3. Instead, a `CompositeTransport` adapter pattern is planned for S8.4, which will implement the existing `Transport` interface while delegating to multiple concrete transports internally.

### 2.4 Problems Faced

**Problem 1: Build structure assumptions**
The engineering brief referenced `pravah-core` as a Maven module and `gradlew` at the repository root. The actual project structure is a single-module Maven project at root with a nested `android/` Gradle subproject. The Gradle wrapper lives at `android/gradlew.bat`, not at the repo root.

**Mitigation:** Ran a build structure discovery pass (Block 1.5) to locate all `pom.xml`, `build.gradle.kts`, `gradlew.bat`, and test source directories before proceeding. Adjusted all subsequent commands to match the real layout.

**Problem 2: Baseline verification ambiguity**
Initial Maven test run with `-pl pravah-core -q` produced no output because the module name didn't exist and quiet mode suppressed the error.

**Mitigation:** Ran `mvn test` at root without module filter and without quiet mode. Confirmed the exact summary line: `Tests run: 319, Failures: 0, Errors: 0, Skipped: 0`. For Android, navigated into `android/` directory and ran `.\gradlew testDebugUnitTest`. Confirmed `BUILD SUCCESSFUL`.

## 3. Sprint S8.2 — Transport-B Foundation

### 3.1 Objective
Implement the smallest working version of Bluetooth RFCOMM transport behind the agreed `Transport` contract, fully testable on the JVM without Android hardware.

### 3.2 What Was Implemented

**`BluetoothRfcommTransport`**
(`src/main/java/com/aryntra/pravah/transport/bluetooth/BluetoothRfcommTransport.java`)

- Implements `com.aryntra.pravah.transport.Transport` interface
- Uses a **Virtual Bluetooth Link Broker** pattern: a static `ConcurrentHashMap<String, BluetoothRfcommTransport> AIRSPACE` simulates the Bluetooth radio environment on the JVM
- Connections use bidirectional `PipedInputStream`/`PipedOutputStream` pairs to simulate RFCOMM streaming channels
- Connection IDs follow the namespace `bt:{MAC}` (e.g., `bt:AA:BB:CC:DD:EE:01`)
- MAC address validation enforces standard format `XX:XX:XX:XX:XX:XX`
- RFCOMM channel validation enforces range 1–30
- Declares `TransportCapabilities`: reliable=true, connectionOriented=true, unicast=true, supportsMultiplexing=false
- Background `readLoop` threads per connection with proper lifecycle management
- Mutual teardown: disconnecting one side cleanly tears down the remote peer's connection descriptor

**`BluetoothRfcommTransportTest`**
(`src/test/java/com/aryntra/pravah/transport/bluetooth/BluetoothRfcommTransportTest.java`)

7 unit tests covering:
1. Lifecycle (start, stop, idempotency)
2. Validation (MAC format, channel range)
3. Capabilities declaration
4. Connection establishment (bidirectional open callbacks)
5. Bidirectional data transmission (A→B, B→A)
6. Disconnect notification (both sides)
7. Error handling (send to unknown destination throws `PravahException`)

### 3.3 Problems Faced

**Problem 3: UTF-8 BOM in generated Java source files**
PowerShell's `Set-Content -Encoding UTF8` writes a UTF-8 Byte Order Mark (`\ufeff`) at the beginning of files. The Java compiler (`javac`) rejects this as an illegal character, producing 17 cascading compilation errors starting with `illegal character: '\ufeff'` at line 1, column 1.

**Mitigation:** Switched all file generation to use .NET's `[System.IO.File]::WriteAllText($path, $content, [System.Text.UTF8Encoding]::new($false))`, which writes UTF-8 without BOM. This pattern was used for all subsequent file generation in S8.2 and S8.3.

**Problem 4: Test isolation with static AIRSPACE registry**
The `AIRSPACE` static map could leak state between tests if transports weren't properly stopped in `@AfterEach`. Early test drafts risked cross-test contamination.

**Mitigation:** Each test's `@AfterEach` calls `transportA.stop()` and `transportB.stop()`, which removes entries from `AIRSPACE`. The `stop()` method also calls `shutdownNow()` on the IO executor and disconnects all active connections. Tests run in ~250ms total with no interference.

## 4. Sprint S8.3 — Hybrid Discovery & Addressing

### 4.1 Objective
Connect the discovery architecture to the new Bluetooth transport without making discovery responsible for connectivity. Enable a single `PeerId` to have multiple reachability candidates across different transports.

### 4.2 What Was Implemented

**`DiscoveredAddressCandidate`**
(`src/main/java/com/aryntra/pravah/peer/discovery/DiscoveredAddressCandidate.java`)

- Transport-agnostic record: `(PeerId, String transportScheme, EndpointAddress)`
- Factory methods: `tcp(peerId, host, port)` and `bluetooth(peerId, macAddress, channel)`
- Deterministic `PathId` generation: `path:{peerId}:{scheme}:{host}:{port}`
- Direct conversion to `ConnectivityPath` in `CANDIDATE` state via `toCandidatePath()`

**`BluetoothPeerDiscovery`**
(`src/main/java/com/aryntra/pravah/peer/discovery/bluetooth/BluetoothPeerDiscovery.java`)

- Simulates Bluetooth device inquiry using a static `ACTIVE_DISCOVERY_NODES` set
- On `start()`, registers in the airspace and performs an immediate scan
- Scan discovers all other active nodes and emits `DiscoveredAddressCandidate` events to registered listeners
- Reciprocal discovery: when node A discovers node B, node B is also notified of node A
- Zero Android SDK dependencies; fully testable on JVM

**`PeerPresenceBridge` Enhancements**
(`src/main/java/com/aryntra/pravah/peer/presence/PeerPresenceBridge.java`)

- New public method: `onCandidateDiscovered(DiscoveredAddressCandidate)` — universal handler for any transport
- Existing `onPeerDiscovered(DiscoveredPeer)` now delegates to `onCandidateDiscovered()` internally by wrapping the LAN discovery as a TCP candidate
- New public method: `handleConnectionClosed(PeerId, String connectionId)` — selectively deactivates a single path by connection ID without dropping other active paths
- `activatePath()` now matches candidates by transport scheme derived from connection ID prefix (`bt:` → bluetooth, else → tcp)
- All existing Phase 3–7 behavior preserved; backward-compatible constructors unchanged

**`HybridDiscoveryTest`**
(`src/test/java/com/aryntra/pravah/peer/discovery/HybridDiscoveryTest.java`)

5 unit tests covering:
1. Single candidate discovery creates deterministic CANDIDATE path
2. Duplicate candidate announcements are idempotent (same PathId, no duplication)
3. Multi-path identity: one PeerId with both TCP and Bluetooth candidates (2 paths, 1 peer)
4. Full lifecycle: CANDIDATE → ACTIVE (both transports) → selective disconnect (Bluetooth only, TCP survives) → full disconnect
5. BluetoothPeerDiscovery airspace simulation emits valid candidates

### 4.3 Problems Faced

**Problem 5: Incorrect assumptions about PeerPresence API**
The initial test draft assumed:
- `PeerPresenceManager` has a no-arg constructor → **Actual:** requires `long presenceTtlMs`
- `PeerPresenceState` has `DISCOVERED` and `DISCONNECTED` values → **Actual:** values are `UNKNOWN`, `AVAILABLE`, `CONNECTED`, `UNAVAILABLE`
- `PeerPresence` uses JavaBean accessor `.getState()` → **Actual:** it's a Java record, so the accessor is `.state()`

**Mitigation:** Inspected the actual source files (`PeerPresenceState.java`, `PeerPresence.java`, `PeerPresenceManager.java`) to determine the real API. Fixed the test to use `new PeerPresenceManager(30_000L)`, `PeerPresenceState.AVAILABLE` / `UNAVAILABLE`, and `.state()`.

**Problem 6: Presence state transition semantics mismatch**
After dropping the last active connection, the test expected `PeerPresenceState.UNAVAILABLE`. The actual `reportDisconnected()` implementation checks whether the peer's `lastSeen` timestamp is still within the TTL window. Since the test runs in milliseconds and the TTL is 30 seconds, the peer is still within TTL, so the state transitions to `AVAILABLE` (not `UNAVAILABLE`).

**Mitigation:** Aligned the test assertion with the actual business logic: `assertEquals(PeerPresenceState.AVAILABLE, ...)`. This is correct behavior — the peer was recently seen and is still discoverable, just not connected. The `UNAVAILABLE` state would only apply after TTL expiry.

**Problem 7: Source file path assumptions**
The engineering brief referenced files under `com.aryntra.pravah.discovery.lan` and `com.aryntra.pravah.routing`. The actual package structure places discovery under `com.aryntra.pravah.peer.discovery` and `PeerRouter` under `com.aryntra.pravah.peer`.

**Mitigation:** Ran recursive file searches (`Get-ChildItem -Recurse -Filter`) to locate the actual paths before attempting to read or modify any files.

## 7. Known Limitations & Forward-Looking Notes

1. **PeerRouter single-transport binding.** `PeerRouter` still holds one `Transport` field. Multi-transport message routing requires the `CompositeTransport` adapter planned for S8.4.

2. **Bluetooth transport is JVM-simulated.** The `BluetoothRfcommTransport` uses virtual pipes, not real Android `BluetoothSocket`. The Android module will need a concrete `AndroidBluetoothRfcommTransport` that wraps the real SDK, likely in S8.5 or S8.6.

3. **No path selection policy.** When multiple active paths exist for a peer, the current `activatePath()` selects by transport scheme match. A formal priority/selection policy (e.g., prefer TCP for bandwidth, prefer Bluetooth for offline resilience) is deferred to S8.5.

4. **No Bluetooth discovery on real hardware.** `BluetoothPeerDiscovery` simulates inquiry. Real Android Bluetooth discovery requires `BluetoothAdapter.startDiscovery()` with broadcast receivers, which belongs in the Android module integration phase.
