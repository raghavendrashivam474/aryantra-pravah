**Before S1.4:**
```
TcpTransport ── activeSocket ── ONE peer
```

**After S1.5:**
```
TcpTransport ── ConcurrentHashMap<String, TcpConnection> ── N peers

                  ├── destination-aware send()
                  ├── independent failure cleanup
                  └── full shutdown teardown
```

## 2. S1.4 — Concurrent Connections: What Was Done

### 2.1 Connection Registry

Replaced the single `volatile Socket activeSocket` and `volatile OutputStream activeOutputStream` fields with a thread-safe connection registry:

```java
private final ConcurrentHashMap<String, TcpConnection> connections = new ConcurrentHashMap<>();
```

Each entry maps a peer identifier (remote socket address string) to a `TcpConnection` container holding the `Socket`, `OutputStream`, and dedicated `readerThread`.

### 2.2 Internal TcpConnection Container

Introduced a private, minimal inner class:

```java
private static class TcpConnection {
    final String id;
    final Socket socket;
    final OutputStream outputStream;
    final Thread readerThread;
}
```

**Design rationale:** This extraction was justified because `TcpTransport` now manages a collection of connections, each with its own socket, output stream, and reader thread lifecycle. Keeping these grouped per-connection rather than scattered across parallel arrays or maps-of-maps is the smallest useful cohesion. The class is `private static` — it does not leak beyond `TcpTransport`.

### 2.3 Connection Identity

Peer identity remains the remote socket address (`socket.getRemoteSocketAddress().toString()`), consistent with the S1.1–S1.3 pragmatic model. No UUID, device ID, user identity, or handshake protocol was introduced. Logical peer identity is explicitly deferred to Phase 2.

### 2.4 Per-Connection Reading

Each accepted or outbound connection spawns an independent daemon `readLoop` thread. A blocked or failed read on one connection does not affect any other connection's reader. The accept loop continues accepting new connections regardless of existing reader state.

### 2.5 Destination-Aware Sending

`send(destinationId, payload)` now performs a three-tier lookup:

1. **Exact match** against the connection registry key.
2. **Normalized match** stripping leading slashes (handles `/127.0.0.1:port` vs `127.0.0.1:port` discrepancies).
3. **Single-connection fallback** — if exactly one connection exists, route to it regardless of destination ID (preserves backward compatibility with S1.3 tests that use arbitrary destination strings like `"server"` or `"client"`).

If no match is found and multiple connections exist, `send()` throws `PravahException`. Broadcasting is not implemented — it is an application-layer concern.

### 2.6 Connection Isolation

A read failure, write failure, or remote disconnect on one connection triggers cleanup of only that connection via `closeConnection(id)`, which atomically removes the entry from the registry, closes the socket and output stream, and interrupts the reader thread (if not the calling thread). Other connections remain fully operational.

## 3. S1.5 — TCP Reliability & Lifecycle: What Was Done

### 3.1 Remote Disconnect Detection

When a remote peer closes its socket, the `readLoop` detects `bytesRead == -1` (end of stream), breaks out of the read loop, and the `finally` block calls `closeConnection(id)`. The connection is removed from the registry. Other peers are unaffected.

### 3.2 Socket Failure / Crash Detection

IOExceptions during read or write are caught at the individual connection level. A failed `send()` closes the target connection and removes it from the registry before throwing `PravahException`. A failed `readLoop` cleans up its own connection in the `finally` block.

### 3.3 Stale Connection Prevention

No connection can remain in the registry after its socket is closed. The `closeConnection()` method is the single point of teardown, called from:
- `readLoop` finally block (remote disconnect or read error)
- `send()` catch block (write error)
- `stop()` (full transport shutdown)
- `attachActiveSocket()` (reconnection with same ID)

### 3.4 Transport Shutdown

`TcpTransport.stop()` now performs the following sequence:

1. Atomically sets `running` to `false` via `getAndSet`.
2. Closes the `ServerSocket` to unblock `accept()`.
3. Iterates all registered connections, calling `closeConnection(id)` on each.
4. Clears the connection registry.
5. Interrupts the accept thread.
6. Nullifies references.

After `stop()`, the registry is empty, no reader threads are alive, and no sockets remain open.

### 3.5 Lifecycle Consistency

Verified that repeated `start()` → `stop()` → `start()` → `stop()` cycles work correctly without port binding failures, thread leaks, or stale state. The `synchronized` keyword on `start()` and `stop()` prevents concurrent lifecycle transitions.

### 3.6 Predictable Failure Modes

| Scenario | Behavior |
|---|---|
| `send()` before `start()` | `PravahException`: "not running" |
| `send()` after `stop()` | `PravahException`: "not running" |
| `send()` to unknown destination (multi-peer) | `PravahException`: "No active TCP connection" |
| `send()` to disconnected peer | `PravahException`: "No active TCP connection" |
| `connect()` before `start()` | `PravahException`: "not running" |

All failures use the existing `PravahException` hierarchy. No new exception types were introduced.

## 4. Architecture Decisions

### 4.1 ADR-002: Multi-Connection TCP Registry

A formal Architecture Decision Record was created at `docs/architecture/ADR-002-multi-connection-tcp-registry.md` documenting:
- The problem (single-connection limitation)
- The decision (ConcurrentHashMap + TcpConnection inner class)
- The consequences (multi-peer support, fault isolation, stable public API)
- The trade-offs (socket-address identity, no framing)

### 4.2 What Was NOT Changed

- `Transport` interface: **unchanged** (getName, start, stop, isRunning, send, setListener)
- `TransportListener` interface: **unchanged**
- `PravahException`: **unchanged**
- `PravahRuntime`: **not wired** to TcpTransport (per brief §24)
- `PravahConfig`, `LifecycleState`: **untouched**
- No new public classes or packages introduced

### 4.3 Helper Method Added

`getConnectionCount()` was added to `TcpTransport` to support deterministic test assertions on registry size. This is a pragmatic testing aid, not a contract change.

## 6. Explicitly Out of Scope (Not Implemented)

The following were deliberately excluded per brief §23:

- Message framing / length-prefix / delimiter protocols
- Wire protocol model (JOIN, MESSAGE, LEAVE)
- Logical peer identity / handshake
- Reconnection / retry / offline queue
- LAN discovery / Bluetooth / adaptive routing
- Android / mobile UI
- PravahRuntime integration
- Any Phase 2 functionality

TCP payloads remain raw `byte[]`. The `one send() ≠ one receive()` limitation is acknowledged and deferred to Phase 2 framing.
