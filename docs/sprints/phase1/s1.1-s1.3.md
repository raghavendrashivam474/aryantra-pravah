## 2. Sprint Breakdown

### S1.1 — TCP Foundation

**Goal:** Prove that Pravah can establish a real TCP connection using `java.net.ServerSocket` and `java.net.Socket`.

**What was done:**
- Implemented `TcpTransport` with server socket binding, connection acceptance via a daemon background thread, and raw byte stream I/O.
- Used ephemeral port binding (port `0`) to avoid port collision issues in parallel test execution.
- Verified the full lifecycle: bind → accept → transfer → stop → resource release.

**Key decision:** Started with a single cohesive class rather than splitting into `TcpConnection`, `TcpSession`, etc. The brief explicitly warned against speculative abstractions, and at this stage one class handles the responsibility cleanly.

### S1.2 — Transport Contract Integration

**Goal:** Turn the TCP experiment into a proper `Transport` implementation that higher layers can consume polymorphically.

**What was done:**
- Ensured `TcpTransport` satisfies every method in the `Transport` interface: `getName()`, `start()`, `stop()`, `isRunning()`, `send()`, `setListener()`.
- Verified polymorphic usage: `Transport t = new TcpTransport(0)` works without the consumer knowing TCP is involved.
- Integrated the `TransportListener` callback so inbound TCP bytes flow through `onDataReceived(senderId, payload)`.
- Added precondition validation: `send()` throws `PravahException` when the transport is stopped or when no active connection exists.

**Key decision:** The `senderId` passed to the listener is currently the remote socket address string (e.g., `/127.0.0.1:54321`). This is a pragmatic placeholder — real peer identity belongs to Phase 2's protocol layer.

### S1.3 — Bidirectional Communication

**Goal:** Two `TcpTransport` instances can exchange raw byte payloads in both directions over a persistent TCP connection.

**What was done:**
- Implemented `connect(remoteHost, remotePort)` for outbound connections.
- Verified Client → Server and Server → Client byte transmission over the same socket.
- Verified multiple sequential payloads maintain ordering and integrity.
- Verified empty payload handling (zero-length `byte[]` transmits without error).
- Verified disconnect detection: when one side stops, the other side's `isConnected()` returns `false` promptly.
- Verified clean shutdown: `start → connect → communicate → stop` completes without hanging threads or test timeouts.

**Key decision:** Used `Thread` (daemon) for the accept loop and reader loop rather than `ExecutorService`. The brief said "choose the smallest mechanism that solves the actual problem." Two daemon threads per transport instance is the minimum viable concurrency model here. An executor pool would be justified when we support multiple simultaneous connections in a future phase.

## 4. Technical Details

### Concurrency Model

| Thread | Type | Purpose | Lifecycle |
|---|---|---|---|
| `TcpTransport-Accept-{port}` | Daemon | Blocks on `ServerSocket.accept()`, attaches incoming connections | Created on `start()`, interrupted on `stop()` |
| `TcpTransport-Reader-{port}` | Daemon | Reads from `InputStream` in a loop, dispatches to `TransportListener` | Created per accepted connection, exits on EOF or `stop()` |

Both threads are daemon threads, meaning they will not prevent JVM shutdown. Both are explicitly interrupted during `stop()`.

### Resource Cleanup

`stop()` executes the following sequence:
1. Sets `running` flag to `false` (atomic).
2. Closes `ServerSocket` (unblocks `accept()`).
3. Closes active `Socket` and `OutputStream` (unblocks `read()`).
4. Interrupts accept and reader threads.
5. Nullifies references.

### Port Binding

`TcpTransport` accepts port `0` for ephemeral binding. The actual bound port is retrievable via `getBoundPort()`. This is critical for test isolation — multiple test cases can run concurrently without port conflicts.

### Thread Safety

- `start()`, `stop()`, `send()`, `connect()`, and `attachActiveSocket()` are `synchronized`.
- `running` is an `AtomicBoolean` for lock-free reads in hot loops.
- `listener`, `activeSocket`, and `activeOutputStream` are `volatile` for visibility across threads.

## 6. Known Limitations & Technical Debt

These are **intentional** and documented here so Phase 2 can address them deliberately:

1. **Single active connection:** `TcpTransport` currently tracks one `activeSocket`. If a second client connects, the first is closed. Multi-peer support requires a connection map, which is a Phase 2+ concern.

2. **No framing protocol:** TCP is a byte stream, not a message stream. Currently, `send()` writes raw bytes and the reader dispatches whatever `InputStream.read()` returns in a single buffer fill. This means large payloads may fragment and small payloads may coalesce. Phase 2 must introduce length-prefix framing or a delimiter protocol before any application-level messaging can be reliable.

3. **`senderId` is a socket address:** The `TransportListener` receives the remote socket address as the sender identifier. Real peer identity (user IDs, device IDs) requires a handshake protocol that does not yet exist.

4. **No integration with `PravahRuntime`:** `TcpTransport` is not yet wired into the runtime lifecycle. `PravahRuntime.start()` does not automatically start a TCP transport. This coupling should be designed carefully in Phase 2.

5. **No reconnection or retry:** If the TCP connection drops, the transport simply marks itself as disconnected. There is no automatic reconnection logic.

## 9. Recommendations for Phase 2

Based on the current state, the natural next steps are:

1. **Wire framing:** Introduce a minimal length-prefix protocol (e.g., 4-byte big-endian length header + payload) so that `send()` and the reader loop can reliably delimit messages over the TCP byte stream.

2. **Connection map:** Replace the single `activeSocket` with a `ConcurrentHashMap<String, Socket>` keyed by peer ID, enabling multi-peer communication.

3. **Runtime integration:** Wire `TcpTransport` into `PravahRuntime` so that `start()` and `stop()` cascade to the transport layer.

4. **Peer identity handshake:** Define a minimal connection handshake so that `senderId` reflects a logical peer identifier rather than a socket address.

None of these should be started until Phase 2 is formally scoped and approved.
