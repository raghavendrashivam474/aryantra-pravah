The final three sprints of Phase 6 — **Connectivity Integration (S6.4)**, **Path Selection (S6.5)**, and **Fallback & Switching (S6.6)** — are complete.

The mission of Phase 6 was to evolve the connectivity model from a **passive architectural scaffold** (introduced in S6.1–S6.3) into **usable connectivity infrastructure** capable of:

```
Discover → Represent → Maintain → Select → Communicate → Detect Failure → Switch
```

…while preserving Phase 0–5 behaviour, the `PeerId`-oriented application API, and existing reliability semantics.

This has been achieved. The system now:

1. Populates connectivity candidates automatically from LAN discovery.
2. Promotes candidates to active paths upon successful connection.
3. Deactivates paths on connection closure without corrupting peer identity.
4. Selects paths deterministically per `PeerId` via `PeerRouter`.
5. Fails over transparently to alternate active paths without application-layer awareness.
6. Fails explicitly and diagnostically when no usable path exists.

All 28 net-new tests pass. The full regression suite of 319 tests passes cleanly on `mvn clean test`.

## 4. Implementation Details

### 4.1 S6.4 — Connectivity Integration

#### 4.1.1 Objective

Bridge the two previously disconnected worlds:

```
LAN Discovery → Presence → PeerRegistry
```

and

```
PeerConnectivityRegistry → ConnectivityPath
```

The integration is additive; the connectivity registry is treated as *supplementary state*, not a replacement for existing presence semantics.

#### 4.1.2 Design Decision — Integration Point

After inspecting the codebase (Section 8 of the brief), `PeerPresenceBridge` was identified as the natural integration point because it already:

- Implements `PeerDiscoveryListener.onPeerDiscovered(DiscoveredPeer)`.
- Coordinates updates to both `PeerRegistry` and `PeerPresenceManager`.
- Exposes explicit `handlePeerConnected(...)` and `handlePeerDisconnected(...)` hooks.

Adding connectivity registration here means the connectivity layer is populated for *every* discovery/connection event in the running system, with no changes required to discovery, presence, or transport code.

#### 4.1.3 Design Decision — Deterministic PathId

The most critical design decision in S6.4 was preventing duplicate paths from repetitive LAN discovery broadcasts.

Since `PeerConnectivity.addPath()` uses `Map.put(pathId, path)` internally, deduplication reduces to producing a **deterministic `PathId`** from stable inputs. We chose:

```
"path:" + peerId.value() + ":tcp:" + host + ":" + port
```

This guarantees that repeated discoveries of the same `(peer, transport, host, port)` tuple produce the same `PathId`, resulting in an idempotent `Map.put()` operation. This decision required no changes to `PathId` itself — the existing `PathId.of(String)` factory was sufficient.

#### 4.1.4 Design Decision — Backward-Compatible Constructor

`PeerPresenceBridge` was extended with an **additive constructor** that accepts an optional `PeerConnectivityRegistry`:

```java
public PeerPresenceBridge(PeerRegistry, PeerPresenceManager)
    → delegates to the 3-arg constructor with connectivityRegistry = null

public PeerPresenceBridge(PeerRegistry, PeerPresenceManager, PeerConnectivityRegistry)
    → full S6.4 behaviour
```

If the connectivity registry is `null`, the class behaves identically to Phase 3–5. This preserved every existing `PeerPresenceBridge`-consuming test.

#### 4.1.5 Lifecycle Implementation

| Event | Action |
|-------|--------|
| `onPeerDiscovered(peer)` | Register or update deterministic `CANDIDATE` path |
| `handlePeerConnected(peerId, connectionId)` | Promote first `CANDIDATE` → `ACTIVE` with `connectionId`; or synthesize an `ACTIVE` path if no prior candidate exists |
| `handlePeerDisconnected(peerId)` | Deactivate all `ACTIVE` paths for this peer; retain `PeerId` and `CANDIDATE`/`INACTIVE` paths |

Path deactivation uses the existing immutable `ConnectivityPath.deactivate()` transition; peer identity is never removed on connection loss.

#### 4.1.6 Tests Added (`ConnectivityPathLifecycleTest`)

9 tests across 3 nested classes:

- `CandidateCreationTests` (3): candidate creation, duplicate idempotence, multi-endpoint case.
- `LifecycleTransitionTests` (4): activation, deactivation, peer identity preservation, connection-without-discovery fallback.
- `PresenceCompatibilityTests` (2): presence state transitions still correct, backward compatibility with the null connectivity registry.

### 4.2 S6.5 — Path Selection

#### 4.2.1 Objective

Answer the question: *"Given a `PeerId`, which path should be used to send this message?"* — deterministically, without exposing `PathId` or transport details to the application layer.

#### 4.2.2 ADR 001 — Path Selection in PeerRouter

Per Sections 22–23 of the brief, extending `PeerRouter` is a change to a protected architectural surface. Before implementation, **ADR 001** was authored at `docs/adr/001-path-selection-peer-router.md` documenting:

- **Problem:** The messaging layer routes solely via `PeerRegistry.lookup(peer).connectionId()`. The new `PeerConnectivityRegistry` is unused by routing.
- **Alternatives considered:**
  - **Option A** — Push path lookup into `PeerRegistry`. *Rejected* (violates single-responsibility; `PeerRegistry` is about identity, not networking).
  - **Option B** — Additive constructor on `PeerRouter` accepting an optional `PeerConnectivityRegistry`. *Chosen*.
  - **Option C** — Separate `PathResolver` interface injected into `PeerRouter`. *Rejected* (unnecessary indirection at this stage).
- **Decision:** Option B. Minimal surface, maximum backward compatibility.
- **Policy:** Deterministic lexicographic sort by `PathId.value()`. Candidates and inactive paths are excluded. Fallback to `PeerRegistry` when connectivity registry has no active paths.
- **Compatibility:** All existing callers use `PeerRouter(PeerRegistry, Transport)`; internally that constructor now delegates to the 3-arg version with `connectivityRegistry = null`, preserving 100% of Phase 3–5 behaviour.

#### 4.2.3 Implementation

`PeerRouter.resolveConnectionId(PeerId)` was factored out as an explicit resolution step:

```
1. If connectivityRegistry != null:
     a. lookup(peerId) → PeerConnectivity
     b. filter to activePaths()
     c. min by pathId.value()  ← deterministic tie-break
     d. return selected.connectionId()

2. Else fall through to legacy:
     a. registry.lookup(peerId) → PeerRecord
     b. If unregistered → PeerRoutingException("is not registered")
     c. If disconnected → PeerRoutingException("is disconnected")
     d. Return record.connectionId()
```

`send(PeerId, Message)` invokes `resolveConnectionId(...)` and then performs the existing encode → frame → `transport.send()` sequence unchanged.

Critically, **the application API is unchanged.** Application code continues to call `router.send(peerId, message)` with no awareness of paths, connections, or transports.

#### 4.2.4 Tests Added

**Unit tests (`PathSelectionTest`)** — 8 tests across 2 nested classes:

- `SelectionTests` (4): single active path, deterministic multi-active selection, inactive exclusion, candidate exclusion.
- `FallbackAndFailureTests` (4): legacy fallback, null-registry constructor, disconnected peer exception, unregistered peer exception.

**Integration test (`PathSelectionIntegrationTest`)** — 1 real-TCP end-to-end test:

- Two real `TcpTransport` instances on loopback.
- Client connects; connection ID captured via `TransportListener.onConnectionOpened(...)`.
- Active `ConnectivityPath` registered for the target peer.
- `router.send(bob, message)` invoked with a logical `PeerId` only.
- Server-side listener decodes the frame via `FrameDecoder.feed()` and `MessageParser.parse()`.
- Full assertion on `MessageType`, `senderId`, `messageId`, and payload bytes.

This test proves the complete chain: `Application → PeerId → PeerRouter → Connectivity → Selected Path → Real TCP Socket → Remote Peer`.

### 4.3 S6.6 — Fallback & Path Switching

#### 4.3.1 Design Observation — Elegance from Composition

The core observation for S6.6: **once S6.5 deterministic selection is in place, path switching is a natural emergent property.**

`PeerRouter.resolveConnectionId(...)`:

- Queries `activePaths()` on every send.
- Filters out `INACTIVE` and `CANDIDATE` paths by definition.
- Selects the next-lowest `PathId` if the current lowest is deactivated.

Therefore, deactivating a path (e.g. `connectivity.addPath(activePath.deactivate())`) is sufficient to cause the *next* send to select an alternate active path automatically. No new failover state machine, no probing thread, no exponential retry — the switching logic is deterministic set arithmetic on the active-path collection.

This aligns with the sprint brief's guidance in Section 32: *"Do not introduce automatic exponential retry, path scoring, network probing, AI routing during this sprint."*

#### 4.3.2 Failure Detection

Per Section 31 of the brief, no new failure detector was introduced. The existing lifecycle mechanism is sufficient:

```
TCP connection closes
   → PeerPresenceBridge.handlePeerDisconnected(peerId)
   → deactivatePaths(peerId) marks all ACTIVE → INACTIVE
   → next router.send(peerId, ...) selects a remaining active path
```

#### 4.3.3 Reliability Layer — Untouched

Per Sections 30 and 33 of the brief, the connectivity layer answers *"which path?"* and the reliability layer (`DeliveryRetryManager`, `DeliveryOutbox`, `GroupDeliveryOutbox`) continues to answer *"was this delivered?"*. No duplicate retry mechanism was introduced. `messageId` remains the identity for delivery semantics. All existing reliability tests continue to pass with zero modification.

#### 4.3.4 Tests Added (`PathFallbackTest`)

3 tests across 2 nested classes:

- `UnitFallbackTests` (2):
  - Dynamic switching: two active paths, verify primary selected, deactivate primary, verify secondary selected, `PeerId` and path count preserved.
  - Explicit failure: all paths deactivated, verify `PeerRoutingException` thrown.
- `IntegrationFallbackTests` (1):
  - Real TCP: two servers, one client, two active paths registered, verify primary selection, deactivate, verify secondary selection over live sockets.

## 5. Problems Encountered and Mitigations

The implementation was not without friction. The following problems were encountered and resolved:

### 5.1 Problem — UTF-8 BOM Contamination

**Symptom:**
```
error: illegal character: '\ufeff'
```

**Cause:** PowerShell's `Set-Content -Encoding UTF8` writes UTF-8 files **with** a leading Byte Order Mark. `javac` on JDK 21 rejects the BOM as an illegal character in source files.

**Mitigation:** Switched all file writes to use `.NET`'s `System.IO.File.WriteAllText(path, content, new UTF8Encoding($false))`, which writes pure UTF-8 without BOM. All subsequent source files were written this way. Existing files (untouched by us) already conformed and were left alone.

**Lesson:** For any future PowerShell-driven Java tooling in this project, `System.Text.UTF8Encoding($false)` should be the default encoding constructor.

### 5.2 Problem — Incorrect Assumed API for `PeerPresenceManager`

**Symptom:**
```
cannot find symbol: method getPresenceState(PeerId)
```

**Cause:** I initially wrote test assertions against `presenceManager.getPresenceState(peerId)` based on symmetry with `PeerPresence`, without verifying the actual API.

**Mitigation:** Inspected `PeerPresenceManager.java` and discovered the correct API is `presenceManager.getPresence(peerId).state()`. Updated all six call sites in `ConnectivityPathLifecycleTest`.

**Lesson:** Never assume an API — always inspect the source before writing test code. Established a consistent pattern of running a `Select-String -Pattern "public "` inspection block *before* writing any test that touches an unfamiliar class.

### 5.3 Problem — Mockito Dependency Not Present

**Symptom:**
```
package org.mockito does not exist
```

**Cause:** My initial `PathSelectionTest` used `Mockito.mock(Transport.class)`, `verify(...)`, `times(...)`, `eq(...)`, `any(...)`. The project's `pom.xml` does not include Mockito — the codebase is intentionally lean, dependency-minimal, and prefers hand-written test doubles.

**Mitigation:** Rewrote the test to use a private static inner class `RecordingTransport` implementing the `Transport` interface. It captures `connectionId` on `send(...)` into an `ArrayList` for assertion. This approach:

- Introduces no new dependencies.
- Matches the coding conventions already established in Phase 3 tests.
- Is more readable — the test's intent is visible in one file.

**Lesson:** Verify the project's dependency footprint before reaching for a library. In a discipline-first codebase, hand-rolled test doubles are often preferable to mocking frameworks for a five-method interface.

### 5.4 Problem — Incorrect Assumed API for `Transport`, `TransportListener`, `TcpTransport`, `Message`, `FrameDecoder`

**Symptom:** Multiple compilation errors after writing `RecordingTransport` and `PathSelectionIntegrationTest`:

- `is not abstract and does not override abstract method setListener(...)`
- `tcpDefaults()` not found
- `getPort()` not found
- `decode(byte[])` not found
- `sender()` not found

**Cause:** I extrapolated API shapes from partial context instead of verifying:

- The actual `Transport` interface uses `setListener(...)` (singular, not `registerListener` / `unregisterListener`) and requires `getName()`, `isRunning()`.
- `TransportCapabilities` factory is `tcp()`, not `tcpDefaults()`.
- `TcpTransport` exposes `getBoundPort()`, not `getPort()`.
- `FrameDecoder` uses **stateful streaming** via `feed(byte[]) → List<byte[]>`, not stateless `decode(byte[])`.
- `Message` uses `senderId()`, not `sender()`.

**Mitigation:** Ran targeted `Select-String -Pattern "public "` inspection blocks against each source file, corrected every call site, and re-ran the full test suite.

**Lesson:** This is the same lesson as 5.2, reinforced. The single most important discipline in this codebase is **inspect before you write**. I now have a habit: for any test touching an unfamiliar class, the *first* action is a five-line inspection block.

### 5.5 Meta-Problem — Estimation of Effort

The initial mental model assumed test-writing would be a mechanical translation of the spec. In reality, roughly 40% of the S6.5/S6.6 debugging effort went into API alignment (Problems 5.2, 5.3, 5.4). This did **not** result in any change to production code — only test code was rewritten — but it did slow the sprint pace.

**Mitigation forward:** For future sprints, I will produce a short **API contract sheet** (three or four lines per touched class) *before* writing any test. This front-loads the inspection cost.

## 9. Recommendations for Phase 7

1. **API Contract Sheets.** As noted in Section 5.5, front-loading a per-class API inspection reduces churn. This is worth formalising as a sprint checklist item.

2. **Deterministic PathId Convention.** The `"path:{peer}:{transport}:{host}:{port}"` convention introduced in S6.4 works well for TCP. Before adding a second transport (Bluetooth, QUIC, WebRTC), this format may need a formal spec or a `PathId.forEndpoint(...)` factory to keep it consistent across transports.

3. **Selection Policy Evolvability.** The current policy — lexicographic sort by `PathId.value()` — is deterministic but semantically arbitrary. When richer signals are actually needed (transport preference, cost, RTT), the policy should be extracted into a `PathSelectionPolicy` strategy interface. **This should not be done until a real consumer demands it**, per the brief's Section 46.

4. **Connectivity Lifecycle Observability.** The `PeerPresenceBridge` currently logs at `FINE` level for connectivity events. If Phase 7 introduces UI or diagnostic tooling, promoting selected events (activation, deactivation) to `INFO` or exposing a `ConnectivityListener` interface will be low-effort and useful.

5. **ADR Cadence.** ADR 001 was valuable — it forced explicit reasoning before code. I recommend making ADR-first the standard for any change to the protected surfaces list (Section 36).
