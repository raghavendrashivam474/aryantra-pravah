## 3. Architectural Investigation (Pre-Implementation)

Before writing any code, the following existing contracts were inspected to understand the current model:

### 3.1 Transport Layer
- **`Transport` interface:** Minimal contract with `getName()`, `start()`, `stop()`, `isRunning()`, `send(destinationId, payload)`, `setListener()`. No capability introspection existed.
- **`TransportListener`:** Functional interface with `onDataReceived(senderId, payload)` and default lifecycle hooks `onConnectionOpened` / `onConnectionClosed`.
- **`TcpTransport`:** Full TCP implementation with `ServerSocket`/`Socket`, concurrent connection registry, `getBoundPort()` method, and connection-scoped reader threads.

### 3.2 Peer Layer
- **`PeerId`:** Immutable value object representing logical peer identity. Deliberately decoupled from IP, port, or socket references.
- **`PeerRecord`:** Java record pairing `PeerId` with a single nullable `connectionId`. Factory methods `connected()` and `disconnected()`.
- **`PeerRegistry`:** Thread-safe `ConcurrentHashMap<PeerId, PeerRecord>` with lookup by `PeerId` or `connectionId`.
- **`PeerRouter`:** Resolves `PeerId → PeerRecord → connectionId → Transport.send()`. Encodes and frames messages before dispatch.

### 3.3 Discovery & Presence
- **`DiscoveredPeer`:** Record holding `PeerId`, `hostAddress`, `port` from LAN UDP discovery.
- **`PeerPresenceState`:** Enum with `UNKNOWN`, `AVAILABLE`, `CONNECTED`, `UNAVAILABLE`.
- **`PeerPresenceBridge`:** Coordinates discovery events into registry and presence updates.

### 3.4 Protocol
- **`Message`:** Record with `type` (MessageType), `senderId`, `messageId`, `payload`.
- **`MessageType`:** Enum with `JOIN`, `MESSAGE`, `LEAVE`. No `ACK` type — application ACKs are sent as `MESSAGE` with `0x02` prefix byte in payload.
- **`ProtocolSessionManager`:** Tracks `JOINED`/`LEFT` states per peer, independent of transport connections.

### 3.5 Key Architectural Finding
The existing model conflated "how to reach a peer" with a single `connectionId` string inside `PeerRecord`. This works for TCP-only but cannot represent:
- Multiple candidate endpoints for the same peer
- Different transport types (TCP vs BLE vs QUIC)
- Path state independent of connection state
- Transport behavioral differences

## 4. HPCA Comparison Analysis

Per the implementation brief, HPCA was used as a design reference — not a dependency.

| Concept | HPCA Model | Pravah S6.1–S6.3 Decision |
|---|---|---|
| Identity | Separate object graph | Existing `PeerId` preserved unchanged |
| Address | Rich endpoint model | `EndpointAddress` (host + port + scheme) — minimal |
| Reachability | Scored path matrix | `PathState` enum (CANDIDATE/ACTIVE/INACTIVE) — no scoring |
| Connection | Full lifecycle state machine | Existing `connectionId` string — unchanged |
| Session | Protocol-level | Existing `PeerState` — unchanged |

**Decision rationale:** HPCA's separation of Identity ≠ Address ≠ Connection is sound and was adopted conceptually. However, HPCA's scoring, ranking, and complex state machines were rejected as premature — no Pravah consumer currently needs them.

## 5. Implementation Details

### 5.1 S6.1 — Connectivity Model

**New package:** `com.aryntra.pravah.connectivity`

**New classes:**

| Class | Type | Purpose |
|---|---|---|
| `EndpointAddress` | Record | Immutable network endpoint (host, port, transportScheme). Factory methods `tcp()` and `of()`. |
| `PathId` | Final class | Unique identifier for a communication path. UUID generation support. |
| `PathState` | Enum | `CANDIDATE` (known endpoint, no connection), `ACTIVE` (connected), `INACTIVE` (closed). |
| `ConnectivityPath` | Record | Binds PathId + PeerId + transportName + EndpointAddress + PathState + optional connectionId. Immutable state transitions via `activate()` and `deactivate()`. |
| `PeerConnectivity` | Class | Aggregates paths for a single PeerId. Thread-safe. Queries: `activePaths()`, `candidatePaths()`, `hasActivePath()`. |

**Tests:** 14 tests in `ConnectivityModelTest` covering endpoint validation, path identity, state transitions, peer connectivity operations, and identity independence.

### 5.2 S6.2 — Multi-Path Peer Representation

**New class:**

| Class | Type | Purpose |
|---|---|---|
| `PeerConnectivityRegistry` | Class | Thread-safe `ConcurrentHashMap<PeerId, PeerConnectivity>`. Supports `registerPath()`, `lookup()`, `lookupByConnectionId()`, `removePeer()`. |

**Key design decisions:**
- One `PeerId` can have unlimited concurrent paths across different transports and endpoints.
- Removing one path does not delete the peer or affect other paths.
- Deactivating one path leaves other active paths usable.
- `lookupByConnectionId()` scans active paths across all peers to find the owning peer.
- **Fully additive:** `PeerRecord`, `PeerRegistry`, `PeerRouter` were NOT modified.

**Tests:** 5 tests in `MultiPathRepresentationTest` covering multi-path registration, single-path removal isolation, deactivation isolation, connectionId lookup across peers, and peer removal.

### 5.3 S6.3 — Transport Capability Model

**New class:**

| Class | Type | Purpose |
|---|---|---|
| `TransportCapabilities` | Record | Four boolean properties: `reliable`, `connectionOriented`, `unicast`, `supportsMultiplexing`. Presets: `tcp()`, `lanBroadcast()`, `defaultCapabilities()`. Fluent `Builder`. |

**Modified files (additive only):**

| File | Change | Risk |
|---|---|---|
| `Transport.java` | Added `default TransportCapabilities getCapabilities()` returning `defaultCapabilities()` | **Zero risk** — Java default method, all existing implementations inherit safe fallback |
| `TcpTransport.java` | Added `@Override getCapabilities()` returning `TransportCapabilities.tcp()` + import | **Zero risk** — explicit truthful override |

**Capability values for TCP:**
- `reliable = true` (guaranteed in-order delivery)
- `connectionOriented = true` (handshake lifecycle)
- `unicast = true` (1-to-1 endpoint)
- `supportsMultiplexing = false` (single byte stream per socket)

**Anti-overengineering compliance:** Only four capabilities were modeled. Speculative properties like `latencyScore`, `bandwidthScore`, `energyCost`, `securityLevel`, `supportsAI`, `internetReachable` were explicitly rejected because no current Pravah consumer needs them.

**Tests:** 7 tests in `TransportCapabilitiesTest` covering TCP preset, LAN broadcast preset, default fallback, builder, equality, TcpTransport integration, and generic Transport default method.

### 5.4 Integration Test

**`ConnectivityIntegrationTest`** (1 test) validates the full real-stack flow:

```
EndpointAddress (discovered)
    → ConnectivityPath (CANDIDATE)
    → TCP connection established
    → ConnectivityPath (ACTIVE) + PeerRegistry registration
    → PeerRouter.send(PeerId, Message)
    → FrameEncoder → TcpTransport → Socket
    → Client receives and parses via MessageParser
    → Client sends ACK (MESSAGE type, 0x02 prefix)
    → FrameDecoder → Server receives ACK
    → Assertions on message type, senderId, messageId, payload
```

This proves the connectivity model works with the real Pravah TCP stack, not just in isolation.

## 6. Problems Encountered & Mitigations

### 6.1 UTF-8 BOM Encoding Corruption
**Problem:** PowerShell's `Set-Content -Encoding UTF8` writes files with a UTF-8 BOM (`\uFEFF`) prefix. The Java compiler (`javac`) rejects BOM characters with `illegal character: '\ufeff'` errors, causing complete compilation failure across all 6 new files.

**Impact:** All 271 existing tests + new tests failed to compile.

**Mitigation:** Applied surgical fix using `[System.Text.UTF8Encoding]::new($false)` to rewrite all generated files without BOM. Established a pattern of always stripping BOM after `Set-Content` for all subsequent file creation.

**Lesson:** PowerShell's `-Encoding UTF8` is NOT the same as UTF-8 without BOM. All future PowerShell-based code generation must use the explicit `UTF8Encoding($false)` pattern.

### 6.2 Integration Test API Mismatches
**Problem:** The initial `ConnectivityIntegrationTest` assumed several APIs that did not match the actual codebase:

| Assumed API | Actual API | Error |
|---|---|---|
| `MessageDecoder.decode()` | `MessageParser.parse()` | `cannot find symbol: class MessageDecoder` |
| `TcpTransport.getPort()` | `TcpTransport.getBoundPort()` | `cannot find symbol: method getPort()` |
| `Message.sender()` | `Message.senderId()` | `cannot find symbol: method sender()` |
| `MessageType.ACK` | No ACK type; ACKs are `MESSAGE` with `0x02` payload prefix | `cannot find symbol: variable ACK` |
| `new FrameDecoder(lambda)` | `new FrameDecoder()` (no-arg constructor, `feed()` returns `List<byte[]>`) | Constructor mismatch |

**Impact:** 9 compilation errors in the integration test.

**Mitigation:** Performed targeted API inspection using `Select-String` across the codebase to discover exact method signatures, field names, and enum values. Rewrote the integration test to match the real APIs:
- Used `MessageParser.parse()` instead of `MessageDecoder.decode()`
- Used `getBoundPort()` instead of `getPort()`
- Used `senderId()` instead of `sender()`
- Sent ACKs as `MessageType.MESSAGE` with `[0x02, messageIdBytes]` payload
- Used `FrameDecoder` no-arg constructor with `feed()` returning `List<byte[]>`

**Lesson:** Never assume API shapes from architectural knowledge alone. Always verify against the actual source before writing integration tests.

### 6.3 Architecture.md File Location
**Problem:** Initial attempt to read `docs/architecture.md` failed — the file is actually at `docs/architecture/architecture.md`.

**Mitigation:** Used `Get-ChildItem -Recurse` to locate the exact path before editing.

## 12. Recommendations for Next Steps

1. **S6.4+ (Future):** Consider wiring `PeerConnectivityRegistry` into `PeerPresenceBridge` so that LAN discoveries automatically populate candidate paths.
2. **S6.4+ (Future):** Consider extending `PeerRouter` to consult `PeerConnectivityRegistry` for path resolution when the primary `PeerRecord.connectionId` is unavailable.
3. **Future transports:** When BLE or QUIC transports are introduced, they should implement `getCapabilities()` truthfully and register paths through `PeerConnectivityRegistry`.
4. **Path selection:** Deliberately deferred. No ranking, scoring, or automatic failover should be introduced until a concrete consumer requirement exists.
